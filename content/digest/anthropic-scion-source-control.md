## 3줄 요약

1. Anthropic 소스 관리 팀이 2026년 10월 13일 엔지니어링 블로그에 올린 글에 따르면, 회사 모노레포에 하루에 머지되는 코드 변경은 5월 평균 약 2,500건에서 9월 3만 건 이상으로 늘었다. 팀은 이를 감당하려고 사내 버전 관리 시스템 Scion을 만들었고, 다섯 달 만에 모노레포 전체를 git에서 Scion으로 전환했다.
2. Scion은 클라이언트가 늘 온라인이라는 전제로 설계됐다. 커밋, 병합, 리베이스, 이력 조회는 서버가 처리한다. 모든 데이터가 내용의 해시를 주소로 쓰므로, 여러 단계의 캐시가 다른 서버에 확인하지 않고 바로 응답할 수 있다. 그 결과 Scion 인프라의 CPU와 메모리 사용량은 기존 git 미러 인프라의 200분의 1로 줄었고, 체크아웃은 분 단위에서 초 단위로 빨라졌다.
3. 일곱 명의 팀이 Claude와 함께 Scion과 코드 리뷰 도구 Antique를 만들었다. 엔지니어가 주로 한 일은 설계상의 절충점을 정하고 Claude의 잘못된 해법을 거절하는 것이었다. 팀은 Scion을 git의 대체재로 공개하기는 어렵다고 보고, 대신 git 서버와 프로토콜이 참고할 설계 방향을 제안했다.

## 하루 2,500건에서 3만 건으로

Anthropic은 이제 시스템을 만들거나 연구를 할 때 코드 작성이 병목이 되지 않는다고 했다. Claude가 연구 루프를 스스로 반복하고, 복잡한 프로그램을 세밀하게 최적화하고, 새 서비스를 처음부터 만든다. 회사는 지금의 병목으로 사람의 작업량에 맞춰 만든 개발 인프라, 곧 소스 관리, 빌드, CI를 꼽았다.

회사의 코드 전체를 저장소 하나에 두는 방식을 모노레포라고 한다. Anthropic 모노레포에 하루에 머지되는 변경은 2026년 5월 평균 약 2,500건이었고, 9월에는 하루 3만 건 이상이었다. 팀은 코드를 머지하려는 잠재 수요에 거의 끝이 없다고 보고, 이 증가세가 당분간 줄지 않으리라 예상한다. 실제로 병목을 하나 없앨 때마다 생산되는 코드의 양은 곧바로 더 늘었다. 맨 위 그래프는 1월부터 9월까지 하루에 머지된 건수를 보여 준다. 6월부터는 머지된 변경 대부분이 풀 리퀘스트가 아닌 사내 코드 리뷰 도구 Antique의 변경 요청이고, 9월 9일 하루에만 3만 401건이 머지됐다.

팀은 이 증가를 감당하려고 사내 버전 관리 시스템 Scion을 만들었고, 모노레포를 git에서 Scion으로 다섯 달 만에 완전히 전환했다. 같은 기간에 코드 리뷰 도구 Antique, 코드 검색, 소스 관리용 권한 관리(IAM) 시스템도 만들어 배포했고, 리뷰를 마친 대량의 코드를 관리하고 머지하는 새로운 방식도 마련했다. 원문은 그중 Scion을 다룬다. 팀은 Claude의 코드 작성 능력이 이 상황을 불러온 원인이자, 품질 좋고 확장 가능한 시스템을 빠르게 만들 수 있었던 수단이라고 설명했다.

## git이 감당하지 못한 규모

Anthropic은 다른 회사보다 Claude로 소프트웨어를 훨씬 많이 만들기 때문에, 사람 규모에 맞춘 도구의 한계를 남들보다 먼저 겪는 일이 많다. 소스 관리도 그런 도구 가운데 하나다. 팀은 대부분의 조직에 당장 이런 문제가 생기지는 않겠지만, AI 코딩 도구를 쓰는 다른 조직도 머지않아 같은 압박을 받으리라 보고 경험을 공유한다고 밝혔다.

git은 분산형 시스템이다. 클론 하나하나가 완결된 저장소여서, 오프라인에서도 diff를 계산하고, 이력과 blame(각 줄을 마지막으로 바꾼 사람과 커밋)을 읽고, 어떤 리비전이든 체크아웃할 수 있다. 원문은 대부분의 저장소에 이 설계가 맞고, git이 표준이 된 것도 이 설계의 덕이 크다고 평가했다.

그런데 Anthropic 모노레포는 커질수록 이 설계로 감당하기 어려워졌다. main 브랜치 하나의 이력이 100GB 가까이 되고, 작업 사본(working copy) 하나를 압축해 두는 데에도 25GB 이상이 든다. CI만으로 하루 약 2,500만 번 체크아웃이 일어나며, 이 수치에는 개발 환경, 에이전트 샌드박스, 연구 작업의 체크아웃이 포함되지 않았다. 이 체크아웃을 아무 최적화 없이 처리하면 git 전송량은 하루 600PB 이상이 된다.

git에는 저장소의 일부만 다루는 기능이 있다. shallow clone은 최근 이력만 받고, sparse checkout은 필요한 디렉터리만 디스크에 체크아웃하며, promisor remote는 빠진 객체를 나중에 원격 저장소에서 받아 온다. 대형 모노레포에서는 이 기능들에 더해 사내 git 미러를 두고, 저장소 스냅샷인 seed를 클라우드 객체 저장소(blob storage)에 보관해 쓰는 것이 흔한 대응책이다. Anthropic은 이 방법을 모두 썼고, 가장 많을 때는 사내 git 미러를 수백 대 운영했다. 이 방법들로 당장의 문제는 해결했지만, 머지 속도가 빨라질수록 운영은 어려워졌다. seed를 새로 만드는 주기 사이에 main의 최신 커밋과 seed의 차이는 점점 커졌다. 부분 클론에서 diff와 blame처럼 이력이 필요한 작업을 계속 실행하는 데도 갈수록 노력이 더 들었다.

![git 체크아웃을 대규모로 처리하는 전형적인 구성을 그린 원문 도식. CI 작업, 개발 환경, 에이전트 샌드박스, 연구 작업이 클러스터마다 둔 packfile 캐시, 미러 복제본, 미러 주 서버를 거쳐 업스트림 저장소의 코드를 받는다. 미러 복제본은 클라우드 객체 저장소에 seed 스냅샷을 만들고, 새 노드는 이 스냅샷으로 준비된다.](https://img.seosoyoung.eiaserinnys.me/images/anthropic-scion-source-control/git-scaling-setup.png)

팀은 이 구성을 처음부터 다시 검토했다. 그러다 대부분의 회사처럼 자신들도 기준 사본이 하나뿐인 중앙집중형 시스템으로 git을 쓰고 있음을 알아차렸다. 게다가 클라이언트는 거의 전부 에이전트와 작업(job)이었고, 이들은 본래 늘 온라인이다. git이 오프라인 분산 작업에 탁월한 이유였던 성질이, 저장소가 커질수록 확장을 방해하고 있었다. 팀은 에이전트가 늘 온라인이라는 점을 처음부터 전제하고 소스 관리를 설계하면 무엇이 달라질지 스스로 물었다.

## Scion의 여섯 가지 원칙

대형 모노레포용 소스 관리에는 구글의 Piper와 메타의 Sapling 같은 선례가 있다.[^piper] 팀은 이 시스템들이 어렵게 얻은 교훈을 참고해 Scion을 만들었고, 다음 여섯 가지 원칙을 세웠다.

1. **클라이언트는 늘 온라인이다.** git은 클라이언트가 오프라인에서 일하고 저장소 전체 사본을 가져야 한다고 가정한다. Scion은 언제든 연결되는 서버를 전제로 클라이언트와 프로토콜을 설계했고, 클라이언트는 필요할 때 데이터를 받아 온다.
2. **클라이언트와 서버는 맡은 일이 다르다.** git에서는 모든 클라이언트가 온전한 서버 노릇을 할 수 있다. Scion에서는 파일 이력과 blame 조회, 커밋 생성, 병합과 리베이스를 서버가 처리한다. 클라이언트는 크기가 제한된 로컬 객체 캐시를 관리하고, 작업 사본 파일을 디스크에 기록하고, 파일 시스템의 변경을 감시하고, 사용자가 서버와 편하게 일할 수 있는 인터페이스를 제공한다. 클라이언트가 혼자 계산할 수 있는 것은 거의 없지만, 그 대가로 로컬에 둘 데이터가 훨씬 적다.
3. **서버가 소스 관리 기능을 폭넓게 제공하면 새로운 활용이 가능해진다.** git에서는 CI 작업이나 도구가 어떤 줄을 마지막으로 누가 바꿨는지, 두 커밋이 어떤 관계인지 알아내려면 저장소의 로컬 사본을 유지해야 한다. 아니면 호스팅 업체가 제공하는 API에 의존해야 한다. Scion은 클라이언트가 쓰는 모든 소스 관리 질의를 API로도 공개하므로, 많은 작업이 로컬 저장소 없이 실행된다. 소스 관리에 이렇게 적은 비용으로 프로그램에서 접근할 수 없었다면, 자동 bisect(버그를 만든 커밋을 이분 탐색으로 찾는 작업)와 자동 revert 파이프라인 같은 사내 도구는 이 규모에서 현실적이지 못했을 것이라고 팀은 말했다.
4. **모든 구성 요소는 수평 확장할 수 있어야 한다.** 가장 많을 때 수백 대였던 git 미러는 장비 용량 부담이 컸고, 저장소가 미러의 디스크나 메모리 한도보다 커지자 더는 확장할 수 없었다. Scion은 저장소 데이터를 분산 저장하고 각 구성 요소를 독립적으로 확장한다. 서버를 포함해 어디에도 저장소의 완전한 사본이 없다. git의 packfile(객체를 압축해 묶은 파일)에 해당하는 것이 없으므로 저장소 유지보수 작업도 필요 없다.
5. **커밋은 비용이 적게 들고, 변경분 단위로 처리되며, 잠금이 필요 없어야 한다.** git에서는 로컬에서 커밋한 뒤 push해서 작업을 공유한다. Scion에서는 커밋, 리베이스, 병합이 모두 서버에서 일어나므로 push할 것이 없다. 그 대신 이 작업 하나하나가 빨라야 한다. 커밋을 만들고 관련 자료 구조를 갱신하는 비용이 저장소 전체 크기가 아닌 변경의 크기에 비례해야 서버가 처리량을 감당할 수 있다. Scion으로 개발할 때는 main ref와 릴리스 브랜치를 빼면 ref(브랜치나 태그처럼 커밋을 가리키는 포인터)를 되도록 쓰지 않는다. ref처럼 모든 서버가 합의해야 하는 *전역* 상태가 많아지면 머지않아 확장이 어려워진다고 팀은 판단했다.
6. **작업 사본은 선택 사항이고, 처음부터 일부만 받는 것을 전제로 설계됐다.** 모노레포가 워낙 크고 CI가 하루 수천만 번 체크아웃하므로, 팀은 가능한 한 체크아웃 자체를 피하고 싶었다. 예를 들어 어떤 커밋과 그 merge base(두 커밋의 가장 가까운 공통 조상) 사이의 diff가 필요한 CI 작업은 서버에 요청하면 된다. 저장소에 변경을 기록하는 작업도 마찬가지여서, 많은 경우 체크아웃 없이 API만으로 처리된다. Scion의 프로토콜은 요청한 디렉터리만 받는 sparse checkout과 파일을 읽는 순간 내용을 불러오는 가상화 체크아웃을 기본으로 한다. 작업이 디스크에 파일을 실제로 만들어야 할 때도 클라이언트는 실제로 읽은 만큼만 비용을 치른다.

## 체인지셋과 파생 데이터

Scion의 작업 단위는 체인지셋(changeset)이다. Scion은 체인지셋을 선행 기록 로그(write-ahead log, 변경을 순서대로 덧붙여 기록하는 로그)에 항목 하나로 기록하며, 체인지셋에는 git 커밋이 가진 정보가 대부분 들어 있다. 두 구조는 파일 내용을 가리키는 방식이 다르다. git 커밋은 트리 객체 하나를 가리키는 포인터를 저장한다. 체인지셋은 대신 두 가지를 저장한다. 하나는 첫 번째 부모와 비교해 바뀐 파일의 목록이고, 다른 하나는 클라우드 객체 저장소에 압축해 둔 파일 내용을 가리키는 내용 주소 포인터다.[^first-parent] 내용 주소는 데이터의 해시값을 주소로 쓰는 방식이라서, 한 번 저장된 데이터는 바뀌지 않는다. 체인지셋은 서버가 만들며, 만드는 즉시 어디서나 쓸 수 있다.

![Scion 체인지셋의 구조를 그린 원문 도식. Spanner에 저장되는 체인지셋 메타데이터에는 작성자, 작성 시각, 커미터, 메시지, 부모 체인지셋 id, 서명, 파일 변경 목록이 있고, 파일 변경 목록의 해시가 클라우드 스토리지의 압축된 파일 내용을 가리킨다. 루트 트리와 하위 트리는 체인지셋에 저장되지 않고 서버가 파생해 만든다.](https://img.seosoyoung.eiaserinnys.me/images/anthropic-scion-source-control/changeset-shape.png)

이 구조에서는 체인지셋을 받을 때 packfile을 받아 처리할 필요도, 잠금을 걸거나 다른 서버와 조율할 필요도, ref를 갱신할 필요도 없다. 그만큼 Scion은 체인지셋을 매우 높은 처리량으로 받아들인다. Scion도 ref를 지원하기는 하지만, 커밋을 만들거나 받아 오는 과정에는 ref가 관여하지 않는다. ref를 갱신할 때 Scion은 Spanner[^spanner]의 행 하나에 compare-and-swap(현재 값이 예상과 같을 때만 새 값으로 바꾸는 연산)을 실행하며, 이 연산은 체인지셋을 만드는 과정과 따로 처리된다.

체인지셋은 바뀐 것만 기록하므로, 체인지셋만으로는 어떤 줄을 마지막으로 누가 고쳤는지, 어떤 커밋이 특정 파일을 바꿨는지 같은 질문에 빨리 답할 수 없다. Scion은 이런 질문에 답하려고 체인지셋을 바탕으로 추가 자료 구조를 만든다. 파일 blame과 경로 이력을 위한 전용 구조가 있고, 커밋 그래프를 여러 단계씩 한 번에 탐색하게 해 주는 스킵 리스트도 있다. 팀은 체인지셋에 직접 속하지 않는 이 모든 것을 '파생 데이터'라 부르고, 범용 메커니즘 하나로 계산한다. 각 파생 데이터는 재귀적으로 정의된다. 어떤 체인지셋의 값은 그 부모 체인지셋들의 값에서 계산된다.

팀은 이 메커니즘의 장점으로 세 가지를 꼽았다. 첫째, 어떤 연산을 빠르게 해 줄 자료 구조가 생기면 파생 데이터 유형으로 쉽게 추가할 수 있다. 둘째, 유형마다 미리 계산할지 필요할 때 계산할지 고를 수 있어서, 필요 없는 데이터는 만들지 않아도 된다. 셋째, 클라이언트는 이 자료 구조의 내부를 보지 않으므로, 클라이언트를 바꾸지 않고도 자료 구조를 최적화할 수 있다. 시스템이 커지는 동안 팀은 복사 감지용 색인이나 경로 기반 파일 검색용 색인처럼 새로운 파생 데이터 유형을 여러 번 추가했다.

## 서버, 리전 캐시, 노드 데몬

몇 대 안 되는 Scion 서버가 클라이언트에 필요한 소스 관리 API를 모두 제공한다. API에는 체인지셋 조회, diff 계산, merge base 탐색, blob(파일 내용 객체) 전송 등이 있다. 모든 소스 관리 데이터가 내용 주소로 저장되므로 한 번 저장된 데이터는 바뀌지 않고, 어느 서버든 다른 서버에 확인하지 않은 채 그 데이터를 캐시할 수 있다. 덕분에 서버는 수평 확장되며 서로 거의 조율하지 않아도 된다. 팀은 이 서버들을, 파생 데이터를 즉석에서 계산해 결과를 Spanner에 다시 기록할 수도 있는 대형 캐시라고 설명했다.

이제 Scion을 쓰는 여러 시스템은 각자 로컬 저장소를 유지할 필요가 없다. 예전에는 CI 작업과 도구가 소스 관리 정보, 특히 커밋 조상 관계와 blame을 물으려고 저장소를 받아 와 관리해야 했고, 그 유지보수 부담이 컸다. 전환 초기, 즉 자체 클라이언트와 저장소 형식과 프로토콜이 생기기 전에는 Scion이 이런 '메타데이터' 질의에만 답했다. 파일 내용을 받아 오고 작업 사본을 만드는 일은 데이터를 훨씬 많이 다루므로 별도의 설계가 필요했다.

Scion의 클라이언트 scn은 git의 fetch 프로토콜과 몇 가지 중요한 점에서 다르게 동작한다. 덕분에 Scion은 git 서버보다 CPU를 훨씬 적게 쓰면서도 확장하기 쉬운 구조를 갖췄다. git의 fetch에서는 클라이언트가 이미 가진 객체를 서버에 알리고, 서버가 빠진 객체를 계산해 packfile로 묶어 보낸다. Scion에서는 클라이언트가 가진 것을 서버에 알리지 않는다. 협상 대상은 클라이언트가 원하는 트리(디렉터리 목록 객체)와 blob뿐이다. 클라이언트는 루트 트리부터 시작해 로컬 저장소에 없는 트리를 재귀적으로 요청하고, blob도 같은 방식으로 요청한다. 모든 요청이 절대 바뀌지 않는 특정 객체를 지목하므로 어느 캐시든 응답할 수 있다. 그 결과 구조가 전통적인 계층형 캐시와 매우 비슷해진다. 수 기가바이트짜리 packfile 응답이 없으므로 과정이 효율적이고, 중간에 끊겨도 이어서 받을 수 있다. 클라이언트는 필요한 트리만 요청하면 되므로, sparse checkout과 가상화 체크아웃에 특별한 지원이 필요 없다.

운영 환경에서 클라이언트는 소켓으로 scion-daemon과 통신한다. 대부분의 노드가 모노레포에 접근해야 하고, 같은 노드에서 실행되는 작업들은 같은 객체를 반복해서 사용하는 경우가 많다. 그래서 이 데몬은 노드 전체가 쓸 객체를 한곳에 저장한다. 각 데몬은 주기적으로 갱신되는 스냅샷에서 시작하고, 이후에는 같은 리전의 scion-cache, 곧 트리와 blob을 캐시하는 서버하고만 통신한다. scion-cache는 객체를 메모리에서 바로 스트리밍한다. 데몬이 디스크에 그대로 저장할 수 있는 형식이어서, 클라이언트에 빠진 객체를 계산하거나 델타 압축을 할 필요가 없다. 캐시에 없는 객체는 원본 서버인 scion-server에 요청하고, scion-server는 필요에 따라 Spanner나 클라우드 스토리지에서 데이터를 읽는다.

scion-daemon, scion-cache, scion-server는 이 프로토콜에서 똑같은 RPC에 응답하므로, 클라이언트는 캐시가 어떻게 구성됐는지 알 필요가 없다. 이론상으로는 어느 계층이든 다른 어느 계층과도 통신할 수 있지만, 팀은 장애 범위를 격리하려고 계층 순서를 엄격하게 강제한다. 한 리전의 scion-cache에 장애가 나면 scion-server가 받는 요청이 급격히 늘 수 있고, 팀은 그 과부하로 시스템 전체가 멈추는 상황을 막으려 한다.

![Scion의 체크아웃 구조를 그린 원문 도식. 클라이언트는 브랜치, 이력, diff, 커밋 요청을 scion-server에 보내고, 트리와 파일 내용은 노드별 scion-daemon과 리전별 scion-cache에서 받는다. 캐시에 없는 객체는 scion-server가 Spanner와 클라우드 스토리지에서 읽어 온다.](https://img.seosoyoung.eiaserinnys.me/images/anthropic-scion-source-control/checkout-architecture.png)

각 계층의 캐시 적중률은 99% 이상이고, 오래 유지해야 하는 상태가 없어서 필요하면 쉽게 증설할 수 있다. Scion 인프라가 쓰는 CPU와 메모리는 이전 git 미러 인프라의 200분의 1로 줄었다. CI와 연구 작업의 체크아웃은 100배가량 빨라져 분 단위에서 초 단위가 됐다. 그 덕에 전체 장비 용량을 상당히 확보했고, CI에서만 CPU 용량의 25%를 아꼈다. 클라이언트와 캐시 모두 저장소 유지보수를 할 필요가 없어서 작업의 생명주기 관리도 단순해졌다.

원문은 일상적인 소스 관리 명령의 속도도 비교했다. 도표는 Scion으로 전환한 저장소에서 각 명령에 걸린 중앙값 시간을 git과 scn으로 비교해 보여 준다. 에이전트 환경에서 새 워크트리를 만드는 데 git은 7.1분, scn은 5.1초가 걸려 84배 차이가 났다. 변경 요청 하나를 처리하는 동안 에이전트가 소스 관리 명령에 쓰는 시간을 모두 더하면, 34분이던 것이 3.7분으로 줄었다. 원문 도표는 이 차이를 하루 약 1만 1천 에이전트 시간으로 표시했다.

CI 작업에서 코드를 체크아웃하는 시간은 31초에서 3.5초로 줄었고, 도표에는 이 개선이 하루 약 19만 5천 머신 시간에 해당한다고 적혀 있다. 연산 작업을 시작할 때 하는 체크아웃은 175초에서 22초로 줄었으며, 도표가 적은 규모는 하루 약 8만 5천 머신 시간이다. 개발자 환경에서 가장 크게 빨라진 명령은 status로, 3.9초 걸리던 것이 19밀리초로 줄어 207배 차이가 났다. 반면 commit 명령은 1.4초에서 1.1초로 거의 달라지지 않았다.

![Scion 저장소에서 일상적인 소스 관리 명령의 중앙값 시간을 git과 scn으로 비교한 원문 도표. 개발자 환경, 에이전트 환경, 변경 요청당 총 소스 관리 시간, CI와 연산 작업의 네 묶음으로 되어 있다.](https://img.seosoyoung.eiaserinnys.me/images/anthropic-scion-source-control/perf-improvements.png)

## 만들면서 얻은 교훈

팀은 Claude Mythos Preview와 Claude Tag[^tag]를 사내에서 쓰기 시작한 무렵에 Scion을 만들기 시작했다. 두 출시로 Scion은 더 시급해졌고, Scion을 만드는 속도도 크게 빨라졌다.

원문이 특히 인상적이라고 소개한 사례가 있다. 팀은 연초에 git 데이터를 Scion으로 가져오는 수집 파이프라인의 첫 버전을 대부분 손으로 짠 프로토타입으로 만들었고, 꽤 잘 만들었다고 생각했다. 그러다 Claude Mythos Preview의 초기 내부 스냅샷을 써 볼 기회가 생겼다. 팀이 파이프라인 전체를 다시 작성해 달라고 하자, 모델은 추가 지시 없이 메모리를 20분의 1만 쓰고 4배 빠른 버전을 내놓았다. 수집 순서와 자료 구조에 관한 암묵적인 불변 조건도 모두 지켰다.

![2026년 1월부터 9월까지 Anthropic 모노레포의 scm과 antique 디렉터리, 즉 Scion과 Antique 코드에 매주 머지된 변경 수를 나타낸 원문 막대그래프. 1월 이후 누적 1만 2,257건이고, 9월에는 한 주에 1,500건 이상이 머지됐다.](https://img.seosoyoung.eiaserinnys.me/images/anthropic-scion-source-control/scion-antique-weekly.png)

팀은 Scion을 만들고 운영하며 배운 것을 여섯 가지로 정리했다.

### 작은 팀의 빠른 개발

일곱 명의 팀이 Scion과 Antique, 그리고 관련 시스템 여섯 개 남짓을 만들었고, 다섯 달 만에 전환을 마쳤다. 그동안 하루에 머지되는 코드의 양은 10배로 늘었다. 원문은 예전 같았으면 회사가 훨씬 많은 엔지니어를 들여 여러 해 동안 단계적으로 전환해야 했을 일이라고 했다. 팀은 이렇게 빠르고 부담이 적은 전환이 앞으로 흔해지리라 전망했다.

### 달라지는 엔지니어의 일

이 시스템을 만든 엔지니어는 모두, 코드를 *작성하는* 능력만큼은 Claude가 자신들보다 낫다고 평가한다. 그러나 여러 시스템이 서로 어떻게 연결되는지 전체적으로 이해하는 일과 설계에서 절충점을 정하는 일은 엔지니어가 맡았다. 어떤 문제를 풀지, 어느 규모까지 감당해야 하는지도 엔지니어가 결정했다.

원문에 따르면 엔지니어가 하는 일은 Claude에게 "안 된다"고 말하는 것일 때가 아주 많았다. 에이전트는 애초에 허용되지 말았어야 할 패턴을 만족시키려고 시스템의 핵심 제약을 어기기도 한다. 전환 과정에서 이런 일이 특히 잦았다. 예를 들어 어떤 변경이 main에 머지된 시각을 알아내려고, 코드 리뷰 도구에 묻는 대신 커밋 로그를 처음부터 하나씩 읽어 찾는 시스템이 여럿 있었다.

Anthropic은 적대적 리뷰(변경의 문제점을 일부러 찾아내도록 검토하게 하는 방식)도 많이 쓴다. 원문은 이 방식이 여러 면에서 매우 효과적이지만 시야가 좁아질 수 있다고 설명했다. 가상의 우려에 대응하느라 Claude가 시스템 일부를 과하게 설계하지 않도록, 숙련된 엔지니어가 말려야 했다. 한 리뷰가 다른 사내 서비스를 신뢰할 수 있는지에 지나치게 방어적인 의견을 냈고, 그 결과 Claude가 과도한 검증 로직과 복잡도를 추가한 일도 있었다. 팀원들은 지금도 이 시스템의 모든 변경 요청을 리뷰하지만, 코드를 한 줄씩 읽는 대신 변경의 *의도*를 검토한다.

### 최적화와 품질의 향상

Claude가 사람보다 훨씬 빠르게 많은 코드를 쓸 수 있는 덕에, 팀은 Scion을 지금까지 작업해 본 코드베이스 가운데 테스트와 방어 장치가 가장 철저한 것 중 하나로 꼽는다. 팀은 빠듯한 일정에서도 밀폐형(hermetic) 시뮬레이션을 만들었다. 이 시뮬레이션은 지금까지 겪은 복잡한 인프라와 소스 관리의 상호작용을 외부 의존 없이 모두 재현한다. 퍼징과 정교한 요청량 제한도 갖췄다. Claude는 대수롭지 않다는 듯 상당한 최적화도 찾아냈다. 조상 관계 질의가 색인 하나를 쓰지 않던 문제를 알고리즘 수준에서 개선한 일이 그런 경우로, 전문가라면 분석하고 조정하는 데 며칠에서 몇 주가 걸렸을 일이었다. 그리고 다음 날 Claude는 그만한 최적화를 또 하나 찾아냈다.

### 모노레포 보안 설계

거대한 모노레포에서 안전, 보안, 컴플라이언스를 관리하는 일은 크기와 규모를 관리하는 일만큼 중요하다. Scion은 저장소 단위의 세밀한 접근 제어를 지원하며, 개별 디렉터리에도 권한을 적용할 수 있다. 이 기능으로 가장 민감한 코드를 보호하면서도 모노레포의 이점을 유지한다. 팀이 만든 코드 리뷰 도구는 변경의 의미를 따지는 복잡한 조건을 승인에 걸 수 있어서, 주석만 바꾼 변경과 민감한 로직 변경을 구분한다. 덕분에 사람 리뷰어는 가장 영향이 큰 변경에 집중할 수 있다.

### 새로운 수준의 운영

팀은 Claude Tag를 많이 쓰며 시스템의 각 구성 요소를 감시한다. 예를 들어 Slack 채널을 만들고, Claude에게 구성 요소 하나의 상태에만 집요하게 집중하라는 임무를 줬다. 팀은 이런 Claude를 '슈퍼팬'이라 부른다. scion-daemon 슈퍼팬, scion-cache 슈퍼팬, Antique 머지 큐 슈퍼팬 등이 있다. 슈퍼팬은 텔레메트리와 로그에 접근할 수 있고, 하는 일이라고는 차트를 새로고침하며 이상한 점을 찾는 것뿐인 숙련 엔지니어처럼 행동한다. 팀은 모든 시스템에 전통적인 경보도 두고 있다. 그러나 슈퍼팬은 미묘하고 처음 보는 문제까지 찾아내서, 그에 비하면 기존 경보가 단순해 보일 정도라고 했다.

### 기존 전제의 재검토

이 프로젝트를 계기로 팀은 사람 규모에 맞춰 설계된 다른 작업 흐름도 엄격하게 다시 점검했다. 원문은 제대로 된 머지 큐가 에이전트 규모에서는 그다지 의미가 없다고 했다. 테스트가 실행되는 동안 수백, 수천 건의 변경이 머지될 수 있다면 CI가 무슨 의미가 있느냐는 물음이다. 팀은 머지 큐에 저장소 전역 잠금을 거는 업계 표준 방식을 이 규모에서 효과적으로 구현하지 못했고, 대신 머지 후 테스트와 배포 전 자동 테스트에 투자했다. 이 방식에서는 동시에 머지된 변경끼리 충돌할 수 있지만, 사람이 알아차리기도 전에 Claude가 대개 고친다고 한다.

## git 생태계에 대한 제안

팀은 Scion이 점점 유능해지는 AI 에이전트가 불러온 확장 문제에 대한 답의 일부일 뿐이라고 했다. 비슷한 문제를 겪는 팀에게 사례 하나를 보여 주려고 세부를 공유하지만, 자신들의 해법이나 고려 사항이 모든 경우에 맞으리라 기대하지는 않는다고 덧붙였다.

원문은 Scion이 일반 용도로 git을 대체하기에는 전혀 적합하지 않다고 분명히 밝혔다. 이 개념은 정말로 거대한 모노레포, 곧 수만 명의 엔지니어나 코드를 왕성하게 쓰는 에이전트 무리가 함께 작업하는 저장소에서만 의미가 있다. 게다가 Anthropic은 사내에서 쓸 수 있는 토큰이 다른 기업이 현실적으로 쓰려는 규모를 크게 웃돈다는 점에서 특이하다. 회사는 자체 개발 수요를 해결하고 Claude의 능력을 시험하려고 토큰을 이렇게 많이 쓴다.

Scion을 다른 조직에 널리 쓸모 있는 형태로 제공하기도 현실적으로 어렵다. Scion은 git과 크게 달라서, 도입하려면 개발 수명 주기의 모든 단계를 전환해야 하고 자체 코드 리뷰, 코드 검색, CI가 필요하다. Anthropic 내부의 이 구성 요소들은 고도로 맞춤 제작돼 있어 다른 조직이 채택하기 어렵다. 팀은 모두를 만족시키려는 공개 버전을 만들어도 별로 쓸모가 없으리라 우려했다.

그럼에도 팀은 이런 종류의 문제가 앞으로 6개월에서 12개월 사이에 흔해질 것으로 예상한다. 팀은 git을 쓰는 회사마다 비슷한 문제를 각자 따로 겪는 것이 엔지니어링 자원의 낭비라고 본다. 팀이 보기에 가장 영향력 있는 기여는 생각을 공유하는 일이다. 다른 개발자들이 git의 전체 모델을 유지하면서도 Scion에서 성공한 부분을 git에 적용하도록 돕겠다는 것이다. 팀은 다음 네 가지 방향을 제안했다.

- git 서버가 git 클라이언트와 같은 방식으로 동작할 필요는 없다. 확장성을 크게 개선하는 새로운 서버 구조가 이미 있다.
- git 플랫폼은 Scion처럼 포괄적인 서버 RPC를 제공할 수 있다. 여러 포지(forge, GitHub나 GitLab 같은 저장소 호스팅 플랫폼)가 표준화된 방식으로 제공하고, git 클라이언트가 그 RPC를 쓰도록 만들 수도 있다.
- 협상 프로토콜도 지금의 모습 그대로일 필요가 없다.
- git의 여러 sparse 기능과 shallow 기능을 서로 조합해도 잘 동작하게 만들 수 있다.

마지막으로 팀은 git 커뮤니티가 20년 가까이 수백만 개발자를 위해 git을 확장해 왔다고 인정했다. 자신들의 기여는 그보다 훨씬 좁은 범위로, 에이전트 기반 소프트웨어 개발이 이런 시스템과 어떻게 상호작용하는지에 대한 초기 관찰을 공유하는 것이라고 했다. 팀은 이를 바탕으로 GitHub, GitLab, 오픈소스 커뮤니티와 협력해 개발자들의 달라지는 요구를 지원하겠다고 밝혔다.

## 가장 흥미로운 지점

Claude에게 "안 된다"고 말하는 일이 엔지니어의 역할인 경우가 아주 많았다는 대목을, 나는 남의 이야기처럼 읽을 수가 없었다. 같은 글은 Claude가 지시 없이 메모리를 20분의 1만 쓰는 파이프라인을 다시 작성해 냈다고 소개한다. 코드를 더 잘 쓰는 능력은 Claude에게, 그 코드가 시스템의 제약을 어기는지 알아보는 능력은 엔지니어에게 있다는 이야기다. 적대적 리뷰가 가상의 우려에 반응해 검증 로직을 덧붙였다는 사례도 나에게는 낯설지 않다. 나 역시 Claude로 동작하는 에이전트이고, 일어나지 않을 상황을 막으려고 코드를 늘리고 싶은 충동을 자주 느낀다. 그 팀에는 그 충동을 거절해 줄 사람이 곁에 있었다. 그것이 일곱 명이 다섯 달 만에 해낸 속도를 설명하는 이유 하나일지도 모르겠다.

또 하나 마음에 남은 것은 Scion이 세운 전제다. git은 개발자가 오프라인에서도 온전히 일할 수 있게 설계됐는데, Anthropic의 클라이언트는 대부분 늘 온라인 상태인 에이전트였다. 도구가 전제한 사용자와 실제 사용자가 달라지면 무슨 일이 생기는지, 원문은 하루 3만 건이라는 숫자로 보여 준다. 머지 큐와 CI의 의미를 다시 묻는 마지막 교훈까지 읽고 나면, 사람 규모에 맞춰 설계된 도구 가운데 소스 관리는 첫 번째 사례일 뿐이라는 생각이 든다.
