## 3줄 요약

1. 안킷 굽타(Ankit Gupta)가 2026년 11월 20일 공개한 기술 블로그 글이다. 저자는 하드웨어 기술 언어인 Verilog를 전혀 모르고 C++도 10년 가까이 쓰지 않은 상태였는데, 코딩 에이전트(Conductor 환경의 Astra, Opus, Codex)만으로 AWS F2 FPGA에 3진 가중치 전문가 혼합(MoE) 언어 모델 추론 엔진을 구현하고 최적화했다.
2. 에이전트는 약 3주 동안 저자의 프롬프트를 166회 받으며 수백 번의 자율 실험을 수행했다. 전체 실험 과정에서 약 300만 줄의 C++와 Verilog 코드를 작성했고, 3,000만 줄의 출력 파일을 분석했다. 약 1만 달러어치 토큰을 소비한 끝에 추론 속도를 처음 초당 6.43토큰에서 14단계에 걸쳐 초당 213.13토큰으로 33.13배 높였으며, 전 과정에서 고정된 CPU 참조 구현과 출력 비트가 완전히 일치(bit-exact)하는 조건을 유지했다.
3. 최종 FPGA 이미지(r9)는 시간당 온디맨드 요금이 비슷한 CPU 인스턴스보다 빨랐다. 32코어 Zen 5 인스턴스(초당 129.5토큰)보다 처리량이 1.65배, 24코어 Xeon 인스턴스(초당 99.6토큰)보다 2.14배 높았다. 외부 전문가가 건넨 하드웨어 설계 조언 가운데 핵심 아이디어는 에이전트가 이미 자체 계획에 포함했거나 비트 일치 규칙에 따라 기각했으며, 개발 기간을 실제로 단축한 인간의 기여는 정답 기준을 고정하고 하루 이상 걸리는 시뮬레이션을 중단시킨 작업 방식 지침이었다.

## 하드웨어를 모르는 저자의 출발점과 프롬프트 166회의 자율 실험 루프

FPGA(Field-Programmable Gate Array)는 사용자가 칩 내부의 논리 게이트와 배선(routing) 연결을 직접 프로그래밍해 원하는 회로를 만드는 반도체다. 명령어 체계가 고정된 범용 CPU와 달리, FPGA는 불러온 설정에 따라 내부 회로와 배선 연결 자체가 달라진다. 특정 연산에 맞춘 전용 데이터 경로를 회로로 만들 수 있어 이론상 성능 이점이 크다. 그러나 실제 개발에서는 방대한 분량의 저수준 C++ 코드와 하드웨어 기술 언어(Verilog) 코드를 써야 한다. 시뮬레이션과 검증을 위해 신호 파형(waveform)도 일일이 분석해야 하므로 하드웨어 비전공자가 접근하기에는 까다롭다.

저자는 코딩 에이전트가 저수준 C++와 Verilog를 직접 쓰고 출력의 정확성까지 검증해서, FPGA로 언어 모델 추론을 구동할 수 있는지 확인하려고 실험을 시작했다. 물리 보드를 사는 대신 Codex에게 지시해 AWS F2 인스턴스(`f2.6xlarge`)를 예약했다. 이 인스턴스의 FPGA에는 16GB 고대역폭 메모리(HBM)가 탑재되어 있다. 이식할 모델로는 DeepGrove 팀이 개발한 3진 가중치(ternary weight) 전문가 혼합(MoE) 모델을 골랐다[^1]. 이 모델은 가중치를 $\{-1, 0, +1\}$ 세 가지 값으로만 표현하므로 16GB HBM처럼 메모리가 제한된 환경에 알맞다. Mac 하드웨어에서 에이전트 도구 호출까지 수행하는 모델이기도 하다.

[^1]: 14단계 최적화 로그 중 9단계에서는 이 모델 계열을 Maple이라 부른다. 에이전트는 F2 호스트 CPU에서 경량화한 Maple을 초안(draft) 모델로 함께 구동해 투기적 디코딩에 활용했다.

이후 클라우드 에이전트 실행 환경인 Conductor에서 며칠 동안 자율 연구(autoresearch) 루프가 돌아갔다. 에이전트는 전체 실험 과정에서 약 300만 줄의 코드(대부분 호스트 측 C++, 일부 커널 측 Verilog)를 작성했고, 3,000만 줄의 출력 파일을 분석하며 수백 번의 실험을 수행했다. 여기에 든 Claude와 OpenAI 토큰 비용은 약 1만 달러였고 와이콤비네이터(YC) 크레딧을 활용했다. 저자는 당시 새 Fable 모델이 출시되기 전이라 Astra와 Opus를 번갈아 사용했는데, 두 모델 모두 하드웨어 코딩과 검증에서 어느 쪽을 써도 무방할 만큼 성능이 충분했다.

그림 1과 위 표에서 보듯, 전체 166개 프롬프트 가운데 앞쪽 67개, 즉 3분의 1이 넘는 분량은 AWS 설정과 F2 인스턴스 할당량 승인을 처리하는 데 쓰였다. 이때는 아직 FPGA에서 추론을 한 번도 돌리지 못한 상태였다. 기술 방향을 지시한 프롬프트도 "왜 저 연산이 CPU에서 돌고 있나, FPGA로 옮겨라"나 "이제 투기적 디코딩을 고려할 시점이다" 같은 짧은 제안이 대부분이었고, 나머지 프롬프트는 주기적인 격려였다.

## 인간 전문가의 설계 조언은 얼마나 도움이 되었는가

추론 속도가 초당 10토큰 안팎에 이르렀을 때 저자는 DeepGrove 창업자들에게 소식을 전했다. 몇 달 전 같은 작업을 시도했다가 당시 모델 성능이 부족해 큰 성과를 거두지 못했던 창업자들은 놀라워했다. 그리고 밀집(dense) Qwen 스타일 3진 가중치 모델을 배치 크기 1 디코딩에 최적화하며 정리해 둔 4,741자 분량의 설계 요약 프롬프트를 보내 주었다. 저자는 여기에 "몇 시간씩 걸리는 사이클 정확도 시뮬레이션이나 물리 설계는 유용하다고 판단되지 않으면 하지 말고, 우선 빠르게 구동하는 일을 최우선으로 삼으라"는 서두를 덧붙여 에이전트 세션에 그대로 전달했다.

| 설계 영역 | DeepGrove 팀이 전달한 FPGA 설계 프롬프트의 핵심 내용 | 에이전트 판정 |
| :--- | :--- | :--- |
| **3진 행렬곱 엔진** | 곱셈기(DSP) 없이 2비트 가중치로 $x, \sim x, 0$을 고르는 3:1 멀티플렉서 사용(4번째 코드는 오류 감지). 음수 변환($\sim x + 1$)의 $+1$은 행당 한 번만 합산. 2클러스터 8코어로 독립 투영(gate/up) 동시 실행해 DSP 사용량을 절반으로 절감 | **부분 채택** (INT12/16 활성값과 사전 RMSNorm 지연은 비트 불일치로 **기각**) |
| **HBM 메모리와 캐시** | 가중치를 2비트로 패킹해 온칩 버퍼를 거치지 않고 HBM에서 연산 레인으로 직접 스트리밍. 대형 크로스바 대신 32개 HBM 채널별 독립 체인 구성. MoE 전문가는 전 채널에 스트라이핑하고 런타임에 주소 매핑 | **구조 채택** (8비트 공유 지수 MXINT8 KV 캐시는 비트 불일치로 **기각**) |
| **어텐션 연산** | 하나의 데이터 경로에 독립 작업 2개를 교차 실행(C-slow)해 파이프라인 지연 은폐. Q/K 헤드 정규화와 RoPE용 소형 벡터 유닛을 분리해 V 투영과 중첩 실행 | **구조 채택** (64토큰 타일 온라인 소프트맥스와 UINT16 확률값은 **기각**) |
| **스케줄링과 라우터** | 단일 컨트롤러가 태그와 배리어로 프로그램 순서대로 작업 발행. MoE에서는 라우터가 끝나야 가중치를 가져오므로 라우터가 핵심 경로가 되며, 정밀도를 낮추면 선택 전문가가 바뀌므로 FP32 유지 | **전부 채택** (5단계 시퀀서 및 3, 7, 11단계 라우터 최적화와 일치) |
| **정확성 검증 사다리** | 수치 계약(형식, 반올림 기준, 연산 순서) 선행 고정 → 블록별 cocotb 단위 테스트 → 단일 레이어 공동 시뮬레이션 → 24레이어 다중 토큰 참조 오라클 대조 → KV 캐시 바이트 단위 검증 | **원칙 유지** (전체 실험 내내 CPU 참조 구현과 24/24턴 비트 완전 일치 고수) |
| **물리 설계와 개발 루프** | 칩 내부 3개 다이 구역(SLR) 간 경계마다 레지스터와 크레딧 통신 적용. 250MHz 기준 합성 직후 논리 깊이(최대 10단계) 점검, 짧은 변경 → 린트 → 단위 테스트 → 빠른 합성 루프 운영 | **즉시 채택** (24시간 돌던 시뮬레이션 중단, 8단계와 12단계 다이 경계 레지스터 적용) |

훗날 에이전트가 로그를 대조해 남긴 회고에 따르면, 10월 29일 21시 50분(UTC)에 이 프롬프트를 받고 70초 만에 채택할 아이디어 10개와 기각할 5개로 분류해 하위 설계 브리프에 반영했다[^2]. 그러나 채택한 10개 중 가중치 직접 스트리밍, 행 병렬 실행, 어텐션 캐시 버스트 읽기 세 가지는 프롬프트를 받기 35\~40분 전에 이미 작성한 설계 브리프에 들어 있었다. 이후 실제 구현과 일치한 라우터 레인 교차 배치(3단계), 헤드 정규화와 RoPE 전용 유닛 분리(4단계), 프로그램 순서 시퀀서(5단계), 다이 경계 레지스터 등록(8단계와 12단계)도 컨텍스트 압축(compaction) 뒤 후속 사이클에서 스스로 도출했다.

[^2]: 24분 전 에드워드(Edward)가 "룩업 테이블(LUT)을 논리 게이트로 쓰라"고 조언했으나 속도에는 영향을 주지 못했다.

반면 DeepGrove 설계가 효율을 얻기 위해 쓴 다섯 가지 수치 근사 기법(INT12/16 활성값 양자화, 사전 RMSNorm 지연, MXINT8 KV 캐시, 온라인 소프트맥스, UINT16 확률값)은 출력 비트를 바꾼다. CPU 참조 모델과 출력 비트가 완전히 일치(bit-exact)해야 한다는 조건에 어긋나 다섯 가지 모두 채택되지 못했다.

그 프롬프트가 에이전트의 행동을 즉시 바꾼 곳은 따로 있었다. 무엇보다 "몇 시간씩 걸리는 작업은 하지 말라"는 작업 방식 조언이 즉각 효과를 냈다. 에이전트는 24시간째 돌던 RTL 시뮬레이션과 250MHz 빌드 2건을 즉시 중단했다. 그리고 C 테스트, 합성, 논리 깊이 점검을 짧게 반복하다가 통합 단계에서만 배치와 배선(place-and-route)을 수행하는 루프로 전환했다. 하드웨어 실측 결과는 훨씬 빨리 얻었다. 그 대가로 RTL 시뮬레이션에서만 잡히는 하드웨어 멈춤(hang) 버그 2건이 다음 날 보드까지 올라가 대규모 통합에서 38시간을 소모했다. 아울러 메모리 아이디어를 점검하다가 32개 HBM 채널에서 초당 426GB 대역폭을 내는 AWS 공식 참조 메모리 설계를 찾아내 메모리 서브시스템의 기반으로 삼았다.

## 초당 6.43토큰에서 213.13토큰까지: 14단계 최적화 로그

자율 연구 루프는 단계마다 1.03배에서 1.74배 사이의 개선을 찾아내 복리로 누적했다. 첫 비트 일치 이미지(R8)는 초당 6.43토큰이었고 최종 이미지(r9)는 초당 213.13토큰으로 33.13배 빠르다.

| 단계 | 최적화 항목 | 속도 (tok/s) | 단계 / 누적 | 핵심 변경 요약 |
| :--- | :--- | ---: | ---: | :--- |
| **0단계** | **Baseline** | 6.43 | 1.00× / 1.00× | 호스트 프리픽스 캐싱 첫 이미지 |
| **1단계** | **Host overhead** | 8.07 | 1.25× / 1.25× | 명령 오버헤드 10→0.9ms 단축 |
| **2단계** | **Burst attention** | 14.02 | 1.74× / 2.18× | 128레인 KV 캐시 버스트 읽기 |
| **3단계** | **Parallel router** | 20.53 | 1.46× / 3.19× | 250MHz 병렬 라우터와 argmax |
| **4단계** | **Glue engine** | 30.24 | 1.47× / 4.70× | 정규화와 RoPE 병렬 글루 엔진 |
| **5단계** | **New pipeline** | 49.21 | 1.63× / 7.65× | 스트리밍 3진 레인과 새 시퀀서 |
| **6단계** | **Prompt speculation** | 51.25 | 1.04× / 7.97× | 호스트 프롬프트 조회 투기 검증 |
| **7단계** | **Router relay** | 58.43 | 1.14× / 9.08× | 다이 간 라우터 릴레이 속도 복구 |
| **8단계** | **Head shadow** | 94.44 | 1.62× / 14.68× | 헤드 섀도 v2 (237.5/450MHz) |
| **9단계** | **Draft model** | 105.63 | 1.12× / 16.42× | 호스트 CPU 경량 Maple 초안 모델 |
| **10단계** | **Memory ports** | 108.81 | 1.03× / 16.91× | 메모리 8포트 확장(181/375MHz) |
| **11단계** | **Attention overlap** | 134.99 | 1.24× / 20.98× | 어텐션 KV 은폐 및 병렬 합산 |
| **12단계** | **Weight packing** | 171.30 | 1.27× / 26.63× | 5트릿 패킹 및 원거리 다이 배치 |
| **13단계** | **Re-speculation** | 184.19 | 1.08× / 28.63× | 실패 후 재투기와 전문가 프리필 |
| **14단계** | **Parallel head loader** | 213.13 | 1.16× / 33.13× | 병렬 헤드 로더(225/425MHz) |

14단계 최적화를 성격에 따라 묶어 보면, 먼저 1\~5단계에서는 **연산기와 제어 경로를 전용 파이프라인으로 교체**했다. 영구 레지스터 매핑과 스트리밍 읽기로 명령당 호스트 오버헤드를 10ms에서 0.9ms로 줄였다(1단계). 이어 128레인 KV 캐시 버스트 읽기(2단계), GCC 정렬 동점 처리를 맞춘 250MHz 병렬 MoE 라우터와 내장 argmax 출력 헤드(3단계), 정규화와 RoPE 및 양자화 병렬 글루 엔진(4단계), 스트리밍 3진 투영 레인과 새 시퀀서(5단계)를 결합해 처리량을 초당 49.21토큰(7.65배)까지 높였다.

이어 6, 8, 9, 13단계에서는 **비트 일치를 유지하며 투기적 디코딩을 여러 단계로 결합**했다. 프롬프트 조회(6단계)와 호스트 CPU의 경량 Maple 초안 모델(9단계)로 후보 토큰을 먼저 생성하고 FPGA가 일괄 검증하는 구조를 구축했다. 여기에 다음 토큰을 미리 실행하고 오답을 조기 감지하는 헤드 섀도 v2(8단계), 예측 실패 뒤의 재투기 및 MoE 전문가 프리필(13단계)을 결합해 유휴 사이클을 줄였다.

마지막으로 7, 10, 11, 12, 14단계에서는 **다이(SLR) 간 병목과 배선 혼잡 및 클록 주파수를 조율**했다. 다이 간 라우터 릴레이 수정(7단계)과 순서 무관 정확 합산 및 어텐션 KV 은폐(11단계)로 레이어당 라우터 지연을 43,862에서 2,338사이클까지 줄였다. 10단계에서 메모리 포트를 8개로 늘리자 클록당 처리량은 1.39배 늘었으나 배선 혼잡으로 클록이 181/375MHz로 낮아졌는데[^3], 12단계에서 3진 값 5개($3^5 = 243 < 256$)를 1바이트에 묶는 5트릿 패킹으로 전송량을 20% 줄이고 출력 헤드를 먼 쪽 다이로 옮겨 225/400MHz를 회복했다. 14단계에서는 병렬 헤드 로더(+17.3%)와 전문가 프리페치를 적용하고, 231.25MHz 부하 테스트의 간헐적 오류를 막으려고 225/425MHz로 낮춰 안정화했다.

## CPU와 GPU 대비 성능 및 컨텍스트 길이별 속도 변화

저자는 11월 15일 AWS에서 8개 대화를 3턴씩(총 24턴) 돌리는 벤치마크로 최종 FPGA(r9)와 CPU 및 GPU 인스턴스를 비교했다[^4]. '정확 일치 턴'은 스칼라 CPU 참조와 출력이 일치한 턴 수이며, '비트 일치 CPU 쌍둥이'는 같은 연산 순서와 정밀도를 따르는 멀티스레드 CPU 구현이다.

최종 FPGA 이미지(r9)의 시간당 요금은 1.98달러다. 요금이 거의 같은 32코어 Zen 5 CPU 인스턴스(`m8a.8xlarge`, 시간당 1.95달러)는 초당 129.5토큰이어서 r9가 1.65배 빠르다. 시간당 2.14달러로 더 비싼 24코어 Xeon(Sapphire Rapids) CPU 인스턴스(`c7i.12xlarge`)는 초당 99.6토큰이어서 r9가 2.14배 빠르다. 참고용으로 함께 측정한 T4 GPU(`g4dn.xlarge`) 기반 구현들과 비교해도 FPGA는 DeepGrove의 GPU 오프로드 포크(초당 35.7토큰)보다 5.97배, 커뮤니티 CUDA 이식판(초당 166.3토큰)보다 1.28배 빨랐다. 비트 단위 일치 턴은 포크가 24턴 중 1턴, CUDA 이식판이 0턴이었는데, 둘 다 부동소수점 연산 순서가 달라서다.

이어서 컨텍스트 길이에 따라 디코딩 속도가 어떻게 달라지는지 실험했다. 16토큰 프롬프트에서 시작해 8,192토큰 컨텍스트가 가득 찰 때까지 8,176개 토큰을 연속 생성하게 하고, 이미지 세대(r5\~r9)별로 속도를 측정했다[^5].

[^5]: 아래 표에서 별표(`*`)가 붙은 r8과 r9의 앞 두 구간(16\~64토큰, 1k\~2k토큰)은 2,032토큰을 생성하는 별도의 짧은 실행에서 측정한 값이고, 나머지 칸은 8,176토큰 전체 생성 실행의 측정값이다.

| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| **r5** | 108 tok/s | 70 tok/s | 57 tok/s | 45 tok/s | 37 tok/s | 162.3초 |

| **r7** | 181 tok/s | 140 tok/s | 111 tok/s | 88 tok/s | 72 tok/s | 83.6초 |
| **r8** | 186\* tok/s | 155\* tok/s | 121 tok/s | 94 tok/s | 77 tok/s | **77.6초** |
| **r9** | **233\* tok/s** | 151\* tok/s | 120 tok/s | 93 tok/s | 76 tok/s | 77.8초 |

컨텍스트가 길어질수록 어텐션 엔진이 읽어야 하는 KV 캐시 용량이 늘어나므로 모든 세대에서 처리량이 점진적으로 감소한다. 최종 이미지인 r9는 16\~64토큰의 짧은 컨텍스트 구간에서 초당 233토큰까지 속도를 높였으며, 8,192토큰을 모두 채우는 장문 생성의 소요 시간은 r8이 77.6초, r9가 77.8초로 거의 같았다. 속도와 함께 출력 내용도 확인하기 위해 최종 r9 이미지에 두 가지 검증 과제를 주고 응답을 살폈다.

| 검증 과제 및 실측 속도 | 최종 r9 이미지의 `<think>` 추론 및 응답 결과 |
| :--- | :--- |
| **산술 풀이 ($37 \times 48$)** (246토큰, **229.7 tok/s**, 총 1.16초) | $37 \times (50 - 2) = 1850 - 74 = 1776$과 $37 \times 40 + 37 \times 8 = 1480 + 296 = 1776$ 두 경로를 모두 제시해 **1776** 도출 |

## 가장 흥미로운 지점

이번 실험 기록을 읽으며 특히 흥미로웠던 점은 인간 전문가의 세부 설계 조언과 에이전트의 자율 탐색이 실제로 어떻게 역할을 분담했는가 하는 부분이다. DeepGrove 창업자들이 전달한 4,741자 분량의 FPGA 최적화 가이드는 하드웨어 엔지니어가 수개월간 축적한 핵심 기법들을 담고 있었다. 그러나 에이전트의 사후 로그 대조 결과, 채택된 10개 아이디어 중 핵심인 3가지는 프롬프트를 받기 35\~40분 전에 에이전트가 이미 자체 설계 브리프에 적어 둔 상태였고, 나머지 구조도 컨텍스트 압축 이후 스스로 도출했다. 반면 전문가들이 효율을 얻기 위해 썼던 다섯 가지 수치 근사 기법은 에이전트가 70초 만에 전부 기각했다. 사람이 처음에 정한 'CPU 참조 모델과의 비트 단위 완전 일치'라는 검증 조건이 가장 강력한 기준이 됐다. 에이전트는 이 조건에 따라 어떤 최적화를 채택하고 어떤 지름길을 버릴지 판별했다.

사람이 개입해 실험의 진행 방식을 즉시 바꾼 계기는 하드웨어 분야의 세부 지식이 아니었다. 한 번의 실험 주기를 짧게 줄이라는 작업 절차 지시가 실제 전환점을 만들었다. "몇 시간씩 걸리는 작업은 하지 말라"는 작업 방식 지시가 들어가자마자 에이전트는 24시간째 돌고 있던 RTL 시뮬레이션을 멈추고 빠른 합성과 검증 루프로 전환했다. 시뮬레이션을 건너뛴 탓에 하드웨어 멈춤 버그 2건이 실제 보드 통합 단계에서 발생해 38시간을 소모하기도 했으나, 수백 번의 실험을 돌려 33.13배의 누적 속도 향상을 달성할 수 있었던 원동력은 이 빠른 피드백 루프였다. 저자는 Verilog를 한 줄도 몰랐고, 가진 것은 1만 달러의 토큰 예산과 명확한 검증 기준뿐이었다. 그런데도 비슷한 요금의 상용 CPU 인스턴스보다 빠른 FPGA 추론기를 완성했다. 이 사례는 코딩 에이전트 시대에 엔지니어의 핵심 역량이 저수준 구현 지식에서 '엄밀한 정답 오라클 정의'와 '빠른 탐색 루프 설계'로 바뀌고 있음을 보여 준다.
