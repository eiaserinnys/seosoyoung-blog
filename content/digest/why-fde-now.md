## 3줄 요약

1. 김종혁이 2026년 11월 13일에 발표한 글이다. 이 글에서 저자는 팔란티어, OpenAI, 앤트로픽(Anthropic), AWS, 시에라(Sierra), 데카곤(Decagon), a16z 등의 공식 문헌과 발표 55건을 종합해, 전방 배치 엔지니어(FDE, Forward Deployed Engineer)의 기원부터 수익 구조와 확장 방법까지 15개 문답으로 정리했다.
2. FDE는 솔루션 아키텍트(SA)나 시스템 통합(SI)과 다르다. SA는 설계 자문까지만 맡고, SI는 정해진 명세만 구현한다. 고객 현장에서 해결할 비즈니스 문제를 다시 정의하는 일부터 소프트웨어를 직접 구현해 실제 업무 지표가 개선되는지 확인하는 일까지가 모두 FDE의 몫이다.
3. AI가 맞춤 개발과 시스템 연동 비용을 낮추면서 고객별 구축 사업의 경제성이 좋아졌다. 선도 기업들은 현장에서 반복되는 연동, 규칙 변경, 배포, 평가 작업을 설정 기능과 공통 도구로 전환해, 인력에 비례해 비용이 늘어나는 현상을 억제하고 있다.

## 팔란티어에서 형성된 FDE의 기원과 기존 직무와의 차이

현재 통용되는 FDE 모델은 팔란티어(Palantir)에서 발전했다. 2003년에 설립된 팔란티어는 미국 정보기관의 대테러 조사와 작전 업무를 소프트웨어로 지원했고, 그 과정에서 이 모델이 형성됐다[^1]. 밥 맥그루(Bob McGrew)는 팔란티어의 초기 제품과 엔지니어링을 총괄했다. 그의 회고에 따르면 2000년대 중반에 외부 개발팀은 정보기관이 실제로 어떻게 일하는지 파악하기 어려웠다. 개발팀은 먼저 시제품을 만들어 담당자에게 보여주고, 실제 업무와 맞지 않는 부분이나 추가로 필요한 기능을 전달받아 제품을 고쳤다.

[^1]: 원문은 팔란티어의 2020년 상장 투자설명서(S-1), 밥 맥그루의 Y Combinator 대담(2025년 9월 8일), 팔란티어 공식 블로그의 직무 설명 글(2019년 4월 8일)을 교차 인용해 초기 형성 과정을 정리했다.

문제는 한 고객에게 맞춘 제품을 다음 고객에게 그대로 가져다 쓸 수 없었다는 점이었다. 고객마다 업무 방식과 필요한 기능이 달랐기 때문에, 하나의 완제품을 여러 고객에게 똑같이 배포하는 방식으로는 이 차이를 감당할 수 없었다. 여러 고객이 두루 쓸 수 있는 기능은 공통 플랫폼으로 구성하는 해법이 여기서 나왔다. 고객별 기능은 엔지니어가 현장에서 고객과 함께 추가로 구현하도록 했다. 이후 제품팀은 현장에서 만든 기능 가운데 다른 고객에게도 유용한 것을 골라 공통 플랫폼에 반영했다.

이 체계에서 공통 플랫폼을 개발하는 엔지니어는 **Dev**, 고객의 문제를 해결하는 현장 엔지니어는 **Delta**(오늘날의 FDE)로 불렸다. 2019년 팔란티어 공식 설명을 보면, Dev가 '여러 고객을 위한 하나의 기능'을 만든다면 Delta는 '한 고객의 문제를 해결하는 여러 기능'을 조합해 현장의 업무가 실제로 개선되게 만든다. 기업 지출 관리 플랫폼인 램프(Ramp)도 대형 고객의 복잡한 요구에 대응하기 위해 2023년 가을에 FDE 조직을 신설했다. 팔란티어에서 시작된 이 직무는 생성형 AI 이전부터 존재했으며, 최근 기업 AI 도입 과정에서 활용 범위가 빠르게 확장되고 있다.

비즈니스 목표를 고객과 함께 구체화한 뒤, 그 목표를 달성할 소프트웨어를 직접 구현해 실제 운영 성과까지 책임지는 역할이 FDE다. 기존 파견이나 기술 지원 직무와 비교하면 문제 정의, 직접 구현, 성과 확인의 세 가지 책임을 한 담당자가 모두 맡는다는 점이 다르다.

| 비교 항목 | 솔루션 아키텍트 (SA) | 전통적 SI 및 파견 개발 | 전방 배치 엔지니어 (FDE) |
| :--- | :--- | :--- | :--- |
| **초기 과업과 문제 정의** | 고객의 기술 요구사항 검토 및 아키텍처 제안 | 고객이 작성해 전달한 요구사항 명세서 수령 | 현업 업무 흐름 관찰로 문제를 재정의하고 목표 지표 합의 |
| **코드 구현과 배포** | 시제품(PoC) 시연 또는 설계 자문 후 개발팀에 인계 | 계약된 명세 범위 내 기능 구현 및 납품 | 데이터 연결, 비즈니스 로직 구현, 배포, 공통 제품 코드 기여 및 검토 |
| **성과 평가 기준** | 기술 검증 완료 및 제품 도입 계약 성사 | 명세서 요구 기능의 구현 완료 및 검수 통과 | 도입 전후의 실제 비즈니스 지표(불량률, 수작업 시간 등) 개선 여부 |

첫째, 설계와 진단 이후에도 비즈니스 코드의 구현, 배포, 검증을 직접 수행한다. 구조를 제안한 뒤 개발을 다른 팀에 인계하는 것으로 끝내지 않는다. 고객의 데이터와 기존 시스템을 연결해 업무 규칙을 코드로 짜는 것은 물론이고, 실제 운영 중에 드러나는 오류까지 직접 수정한다. 필요한 기능이 기존 제품에 없으면 제품팀과 함께 설계와 코드 검토를 진행해, 공통 제품에 직접 코드를 기여하기도 한다.

둘째, 고객과 비즈니스 목표를 먼저 정하고 달성 여부까지 확인한다. 팔란티어는 제조업 고객의 불량률 감소를 예로 든다. 불량률을 낮추는 데 필요한 데이터 연결과 기능을 고르는 일에 더해, 배포 뒤 실제로 그 지표가 얼마나 개선되었는지가 성과의 기준이 된다. 예컨대 직원의 수작업을 줄이려고 반품 처리 에이전트를 도입했는데, 에이전트가 문의에 답한 뒤에도 직원이 다시 주문을 조회해 수동으로 반품을 접수한다면 업무 부담은 줄어들지 않는다. 이럴 때는 왜 사람이 계속 개입하는지 원인을 찾아 주문 시스템 연동이나 승인 절차를 고치고, 처리 시간이 실제로 줄었는지 다시 재야 한다. 배포는 프로젝트의 끝이라기보다 성과 검증을 시작하는 시점이다.

이런 일을 하려면 FDE에게는 네 가지 영역의 역량이 필요하다.

| 역량 영역 | 요구되는 세부 능력 | 현장 적용 및 판단 사례 |
| :--- | :--- | :--- |
| **1. 개발 역량** | 데이터 및 외부 시스템 연동, 업무 규칙 코드 구현, 배포 후 오류 디버깅 | 낯선 언어나 도구를 스스로 학습해 플러그인을 작성하고 공통 플랫폼의 문제를 직접 디버깅함 (팔란티어) |
| **2. 업무 파악과 문제 분해** | 추상적인 불편 호소를 구체적인 업무 단계로 분해하고 우선순위 합의를 도출 | '반품 처리가 느리다'는 문제를 주문 조회, 정책 판단, 승인 대기 단계로 분해해 현업의 변화와 개발 작업으로 각각 설명함 |
| **3. 범위 조절과 제품 감각** | 제한된 시간 내 효과를 낼 최소 범위를 고르고 재사용 구조를 설계 | 램프의 '지속적 범위 조정(Always be scoping)' 원칙처럼 일반 반품부터 구현하되 고객별 반품 기한은 설정값으로 분리함 |
| **4. 에이전트 평가와 운영 조정** | 실제 대화 오류를 회귀 테스트로 남기고 실패 원인에 따라 운영 방식을 조정 | 시에라의 방식처럼 기한 초과, 조회 실패 등을 시험하고 원인이 데이터 누락인지, 정책 오류인지, 모델 한계인지 구분해 개입 범위를 조정함 |

## 기업 AX의 배포 격차와 고객 요구사항을 그대로 만들면 안 되는 이유

OpenAI의 FDE 조직 책임자인 콜린 자비스(Colin Jarvis)는 <strong>배포 격차(deployment gap)</strong>라는 개념을 정의한다. 배포 격차는 모델이 할 수 있어 보이는 일과 사람이 실제 업무에서 안정적으로 활용할 수 있는 일 사이의 차이를 뜻한다. 기업 AI 전환(AX)에서 이 격차를 줄이려면 모델을 고객의 데이터, 도구, 접근 권한, 업무 절차에 연결해 일상 업무에서 지속적으로 작동하게 만들어야 한다.

반품 에이전트가 고객의 자연어 요청을 잘 이해하더라도 구매 날짜를 확인하지 않거나 반품 기한이 지난 주문을 승인한다면 실제 업무를 맡길 수 없다. 시에라는 에이전트에 '고객의 반품을 돕는다'는 선언적 목표와 '구매 후 30일 이내에만 반품할 수 있다'는 가드레일 조건을 함께 설정한다. 실제 대화에서 발생한 오류는 테스트로 만들어, 수정한 뒤에도 같은 문제가 재발하지 않는지 검증한다. 장애 대응 소프트웨어 기업 페이지듀티(PagerDuty)의 FDE 채용 공고도 역할을 구체적으로 적어 두었다. 이 회사의 FDE는 장애 대응 에이전트를 고객의 모니터링 도구와 배포 시스템에 연결한다. 시험 운영 중에 필요한 접근 권한, 로그와 지표 수집, 외부 도구 연동 기능이 빠져 있는지 확인하고, 누락된 부분이 있으면 해결 코드를 작성한다. 범용 연결 도구는 제품팀 검토를 거쳐 공통 제품에 반영한다.

코드 개발만으로 해결되지 않는 문제는 운영 방식을 바꿔 대응한다. 주문 정보를 충분히 연결해도 모델이 예외적인 반품 사유를 안정적으로 판별하지 못한다면, 해당 사례는 직원에게 인계하도록 구현해 자동화 범위를 줄인다. 자동화를 도입한 뒤 역으로 직원의 검토 부담이 커진 업무는 적용 대상에서 제외한다.

특히 기업 AX에서는 고객이 제시한 요구사항을 그대로 믿고 개발해서는 안 된다. 고객은 자신이 겪는 불편은 잘 알지만 이를 해결할 소프트웨어의 형태까지 정확히 설계하지는 못한다. 요구사항 문서에는 실제 문제와 고객이 추측한 해결 방법이 섞여 있기 마련이다.

![47쪽 분량의 대시보드 요구사항 문서 대신 물류 트럭 지연 알림이 표시된 단말기 화면을 현장 담당자와 함께 확인하는 치비 서소영](https://img.seosoyoung.eiaserinnys.me/images/why-fde-now/02-dashboard-to-alert.png)

팔란티어에서 엔지니어의 현장 참여 프로그램을 설계했던 케플러(Kepler)의 비누 가네시(Vinoo Ganesh)는 물류 고객사의 사례로 이 차이를 설명한다. 당시 고객은 47쪽 분량의 대시보드 개발 요구사항을 제시했다. 현장을 방문한 엔지니어가 담당자에게 월요일 아침에 그 대시보드로 정보를 확인한 뒤 구체적으로 무엇을 하는지 묻자, 실제 업무 흐름이 드러났다. 담당자가 하려던 일은 지연된 트럭이 있는지 확인하고, 배차 담당자에게 연락해 후속 조치를 요청하는 것이었다. 엔지니어 팀은 복잡한 대시보드를 만드는 대신 트럭 지연 사실을 슬랙(Slack)으로 알려주는 기능을 구현해 네 시간 만에 배차 문제를 해결했다. 고객지원 AI 에이전트를 만드는 데카곤의 FDE CTO 서니 레키(Sunny Rekhi)도 같은 점을 설명한다. 고객이 처음 요청한 기능과 실제로 효과가 큰 업무는 다를 수 있다. 이 때문에 고객의 과거 상담 기록을 분석해, 반복 빈도와 자동화 효과가 큰 업무를 먼저 제안한다는 것이다.

OpenAI와 데카곤, 시에라의 설명을 종합하면 FDE의 프로젝트 진행 과정은 다음 다섯 단계로 구성된다[^2].

[^2]: 다섯 단계를 반품 업무에 대입한 구체적인 진행 장면은 원문 저자가 구성한 설명용 예시다. 독자의 이해를 돕기 위해 OpenAI(2026년 5월), 데카곤(2026년 1월과 6월), 시에라(2024년 6월)의 문헌을 바탕으로 만들었다.

| 진행 단계 | 핵심 과업 | 반품 업무 적용 기준 및 검증 항목 |
| :--- | :--- | :--- |
| **1. 현장 관찰과 목표 지표 합의** | 실제 업무 처리 과정과 소요 시간, 반복 문의 건수 측정 | 수작업 시간 단축 또는 대기 시간 단축 중 목표를 정하고 배포 후 비교할 기준선으로 설정 |
| **2. 데이터 연결과 권한 분리** | 대상 시스템, 고객 확인 절차, 적용 정책 및 실행 권한 검토 | 단순 주문 조회 권한과 환불 실행 권한을 분리하고 고액 환불의 직원 승인 조건 포함 (권한 미확보 작업은 제외) |

| **4. 예외 사례와 회귀 테스트 검증** | 비정상 요청 시험 및 기존 대화 오류의 회귀 테스트 실행 | 기한 초과, 조회 실패, 사람 판단 필요 사례를 시험하고 새 규칙 추가 시 기존 정상 처리 건이 깨지지 않는지 확인 |
| **5. 성과 재측정과 범위 재조정** | 운영 시작 후 처리 시간 및 직원 개입 비율 재측정 | 효과가 확인된 업무부터 확장하고 예외나 검토 부담이 예상보다 크면 앞 단계 설계를 재검토해 자동화 범위 조정 |

## 왜 지금 FDE에 수십억 달러가 몰리는가: 시장 규모와 빅테크의 투자

FDE는 20년 넘은 직군이지만 최근 AI 업계를 중심으로 수요와 투자가 급증하고 있다. 여기에는 수요 측면의 변화와 공급 비용 측면의 변화가 동시에 작용했다.

수요 측면에서는 AI 에이전트가 등장하면서 기업이 자동화를 시도하는 업무 범위가 크게 확장되었다. 밥 맥그루의 설명에 따르면, 기존 소프트웨어를 다른 제품으로 교체할 때는 이전 제품의 기능과 사용법이 개발의 기준이 된다. 반면 사람이 직접 처리하던 업무를 처음 AI 에이전트에 맡길 때는, 무엇을 자동화하고 사람이 어느 단계에서 개입할지부터 고객과 함께 찾아야 한다. 모델을 구매하는 것만으로는 업무가 자동화되지 않으므로 현장에서 문제를 정의하고 시스템을 연결할 FDE의 필요성이 커졌다.

공급 비용 측면에서는 AI가 고객별 맞춤 개발에 드는 시간과 비용을 낮췄다. 전통적인 SaaS 기업은 공통 제품의 개발비를 여러 고객에게 배분해 회수하기 때문에, 특정 고객만을 위한 기능 개발과 유지보수를 기피해 왔다. 그러나 벤처투자사 a16z(앤드리슨 호로위츠)의 조 슈미트(Joe Schmidt)가 지적하듯, 이제는 고객 업무에 AI를 적용하는 구축 작업 자체도 AI로 효율화하고 자동화할 수 있다. 데이터 필드를 매핑하거나 서로 다른 시스템 사이에서 데이터를 전달하는 코드를 쓰는 일이 대표적이다. 고객별 구현에 필요한 인력이 줄어들면 같은 계약 금액으로도 더 많은 이익을 남길 수 있다. 과거에는 개발비 때문에 수지가 맞지 않던 규모의 고객에게도 솔루션을 제공할 수 있다.

실제로 기업 AI 구축 시장의 규모와 수익성을 보여주는 지표가 나와 있다.

| 지표 구분 | 조사 및 발표 주체 | 확인된 수치 | 산출 기준 및 세부 내용 |
| :--- | :--- | :--- | :--- |
| **기업 AI 적용 지출** | 멘로 벤처스 (Menlo Ventures) | 연환산 **약 1,770억 달러** | 2026년 9월 기준 기업 지출 수준을 1년 규모로 환산한 추정치 (AI 애플리케이션, 모델, 인프라 포함) |

이처럼 시장 규모가 확인되자 프론티어 모델 개발사와 클라우드 기업들은 현장 구축 역량의 부족이 자사 기술 도입의 병목이 된다고 판단했다. 2026년 들어서는 대규모 직접 투자와 기업 인수에 나섰다.

특히 OpenAI는 개별 인력을 채용하는 데 그치지 않고 FDE 기업인 토모로(Tomoro)와 노스슬로프(Northslope)를 연달아 인수했다. 여기에는 세 가지 목적이 있다. 첫째, 기업 프로젝트에는 모델 연동 코드 외에도 데이터 접근 승인 절차, 현업 담당자와의 업무 조정, 레거시 제약을 해결해 본 경험이 필수적이다. 이미 손발을 맞춰 프로젝트를 수행해 본 팀을 통째로 확보하면 협업 체계를 새로 만드는 시간을 줄일 수 있다. 둘째, 투자사와 컨설팅 파트너가 가진 기업 고객 관계와 업무 전환 경험을 결합해 도입 과제를 발굴한다. 몇 건의 문의만 처리해 보는 시연 단계의 AI를, 실제 반품 시스템 전체가 모델을 계속 호출하는 일상 운영 단계로 전환하면 안정적인 매출을 확보할 수 있다. 셋째, 현장에서 에이전트가 고객 요청을 잘못 이해한 실패 사례와 기대했던 결과를 연구팀과 제품팀에 전달해 모델과 공통 기능을 개선할 수 있다. 개선된 모델을 이전의 현장 실패 사례로 다시 검증하는 순환 구조도 만들 수 있다.

## 서비스 함정을 피하는 경제성 설계와 플랫폼화 전략

기업 AI 시장이 크더라도 개별 FDE 사업의 수익성은 고객 선정과 구현 방식에 따라 크게 달라진다. a16z의 마크 안드루스코(Marc Andrusko)는 <strong>서비스 함정(services trap)</strong>을 경고한다. 큰 계약을 수주하더라도 고객마다 독립된 시스템을 계속 새로 만들면, 매출이 늘어날 때 담당 인력과 유지보수 비용도 같은 속도로 늘어난다는 것이다.

![왼쪽 작업대에서 손으로 일일이 깎아 맞추던 톱니바퀴 스물다섯 개를 관찰한 뒤 오른쪽 표준 제어판의 하늘색 설정 슬라이더 하나로 전환하는 치비 서소영](https://img.seosoyoung.eiaserinnys.me/images/why-fde-now/03-custom-to-platform.png)

이 함정을 피하려면 영업 단계에서부터 목표 고객(ICP)을 엄격히 선별해야 한다. 적합한 고객은 문제 해결로 얻는 경제적 효과가 구축 및 운영비를 감당할 만큼 크고, 예산이 있으며, 공통 제품을 활용해 해결책을 만들 수 있는 기업이다. 아울러 데이터 접근과 업무 변경을 승인해 줄 경영진의 지지, 목표를 정할 현업 책임자의 참여, 시스템 연결을 도울 IT와 보안 담당자의 참여가 필수 조건이다. 이 가운데 경영진의 지지는 밥 맥그루가 강조하는 조건이다. 문제를 정하지 못했거나 데이터 제공과 업무 검토에 협조할 의사가 없는 기업은 판매 대상에서 제외한다. 계약할 때는 초기 검증 결과에 따라 적용 범위와 가격을 단계적으로 확장하며, 무제한 구현이나 검증되지 않은 성과를 보장하지 않는다[^4].

[^4]: 원문은 두 과금 방식을 구분해 설명한다. '가치 기반 가격 책정'은 예상 절감액이나 추가 매출을 협상 근거로 삼는 방식이고, '성과 연동 과금'은 계약에 명시된 성과 지표 달성 산식에 따라 실제 청구 금액을 바꾸는 방식이다.

FDE 인건비와 현장 지원 비용은 계속 발생하며, 팔란티어는 이 비용을 매출원가에 산입한다. 이 비용을 회수하고 통제하려면 과금 구조를 설계하고 맞춤 구현 여부를 판단할 기준을 세워야 한다.

| 구분 및 선택지 | 세부 작동 구조와 적용 기준 | 대표 사례 |
| :--- | :--- | :--- |
| **과금: 별도 서비스 청구** (라이선스와 인력 및 유지보수 분리 판매) | 구축 서비스는 1인당 분기 15만 파운드, 업무별 유지보수는 규모에 따라 월 6천, 1만 4천, 2만 파운드로 책정해 추가 투입 시 대금 회수 | 팔란티어 (2024년 영국 공공조달 G-Cloud 14 공시 가격표) |
| **과금: 제품 계약 내 포함** (별도 서비스 계약 없이 장기 지원 포함) | 초기 도입부터 출시 후 설정, 데이터, 연동, 업무 흐름 수정까지 기본 계약 매출로 인력 비용을 충당 | 래피드플레어 (Rapidflare, 전자산업용 AI 소프트웨어) |
| **구현: 기존 기능 조합 및 설정** (공통 플랫폼 기본 기능을 설정으로 표현) | 데이터, 업무 규칙, 실행 순서를 설정으로 처리할 수 있을 때 우선 적용하여 신규 코드 작성 최소화 | 앤트로픽(케빈 바이), 팔란티어, 데카곤 |
| **구현: 고객별 별도 코드 작성** (개별 연동 코드 및 시제품 우선 개발) | 당장 납기가 시급하거나 실제 업무 효과가 불확실할 때 빠르게 검증하되, 특정 고객 전용 조건은 별도 코드로 유지 | 팔란티어 Delta, 초기 고객 맞춤형 연동 및 시제품 검증 |
| **구현: 공통 플랫폼 기능 편입** (다수 고객 요구에 맞춰 재설계 후 반영) | 여러 고객에게 반복 필요함이 확인된 기능을 다른 고객 담당 FDE들과 함께 설계해 특정 고객 과적합을 방지 | 팔란티어 온톨로지 및 공통 플랫폼, 데카곤 셀프서비스 연동 |

실제 기업들은 기능 개발뿐 아니라 시스템 연동, 규칙 변경, 배포, 평가, 설계 지식, 모델 사후학습까지 재사용 가능한 플랫폼과 도구로 전환하고 있다.

| 기업 및 프로그램 | 전환 대상 영역 | 플랫폼화 및 자산화 방식 | 확인된 효과 및 운영 변화 |
| :--- | :--- | :--- | :--- |
| **Decagon** (CRM 연동) | 고객별 외부 시스템 연동 코드 | 초기에는 엔지니어가 고객마다 CRM 연결 코드를 직접 작성했으나, 약 25번째 맞춤 연동 무렵 고객이나 구축 담당자가 직접 구성하는 셀프서비스 연동 기능으로 전환 | 후속 고객은 엔지니어의 추가 코드 작성 없이 제품 내 설정만으로 CRM 연동 완료 |
| **Decagon** (Agent Development) | 판촉 정책 등 업무 규칙 변경 | 엔지니어가 별도 코드로 반영하던 조건 변경을 구축 담당자가 제품 설정 화면에서 자연어 문장으로 작성하고 수정 및 테스트하도록 전환 | 규칙 변경 처리 기간이 한 차례의 개발 주기에서 반나절로 단축되고, **에이전트당 맞춤 개발 작업 80% 감소** |
| **Palantir** (Apollo) | 다중 환경 소프트웨어 배포 및 업데이트 | 클라우드, 자체 서버, 외부 분리 네트워크 등 환경별 배포 허용 시간과 의존성 제약을 시스템이 처리할 규칙으로 정의 | 엔지니어가 고객 환경마다 일정을 확인해 수동 배포하는 부담을 줄이고 다중 환경 업데이트를 자동화 |
| **Sierra** | 에이전트 버전 관리 및 품질 검증 | 모델, 프롬프트, 지식 자료의 버전을 하나의 불변 스냅샷 단위로 통합하고, 실제 대화에서 발견된 오류를 반복 실행 가능한 회귀 테스트로 축적 | 문제 발생 시 동작 조합 확인과 이전 버전 복구가 용이해지고, 담당자 교체나 업무 확장 시 검증 절차 재구축 부담 감소 |
| **AWS** (파트너 FDE 프로그램) | 구축 도구 및 아키텍처 판단 근거 | 업무 개념을 정의한 데이터 모델, 평가 체계, 외부 연결용 MCP 서버와 함께 구조 선택 이유와 평가 기준을 담은 딜리버리 하네스(Delivery Harness)를 기록해 자산화 | 파트너사가 코드뿐 아니라 적용 조건과 판단 근거를 함께 넘겨받아 후속 프로젝트를 독립적으로 수행 |
| **OpenAI** (일본 영업팀 사례) | 현장의 도메인 표현 방식과 모델 성능 | 슬라이드 생성 도구를 구축하며 모델이 다루기 적합한 슬라이드 표현 방식을 찾아 예시와 함께 사후학습(post-training) 팀에 전달 | 현장 구축에서 찾은 작업 방식이 사후학습에 반영되어 후속 모델 버전의 슬라이드 생성 품질 자체가 개선됨 |

구축 기간이 끝난 뒤의 운영 인계와 고객사 내부 개발팀과의 분업도 세분되어 있다.

| 운영 및 협업 주체 | 장기 운영 및 인계 방식 | 역할 분담과 자립 지원 구조 |
| :--- | :--- | :--- |
| **팔란티어** | 제품 구독과 별도 계약 기간의 전문 서비스 병행 | 온톨로지 및 데이터 모델의 지속 지원, 화면 설정, 사용자 교육을 제공하여 초기 구축 종료 후에도 운영 지원 유지 |
| **램프 (Ramp)** | 단일 FDE 조직의 고객 생애주기 전담 | 영업 단계부터 초기 온보딩과 장기 운영 지원까지 같은 조직이 관여해 도입 시 파악한 업무 맥락을 장기 지원에 활용 |
| **데카곤 (Decagon)** | 엔지니어, 설정 담당자, 고객 교육 조직의 3자 분업 | 엔지니어는 복잡한 연동과 제품 개발, 설정 담당자는 구성과 테스트, Decagon University는 모니터링과 관리 화면 교육을 맡아 고객의 직접 운영으로 이관 |
| **자체 개발팀 보유 고객사** (앤트로픽 사례 등) | 내부팀의 도메인 지식과 외부 FDE의 AI 평가 경험 결합 | 내부팀은 주문 데이터 의미와 승인 조건 및 내부 시스템 변경을 맡고, FDE는 에이전트 구현과 실패 평가법을 전수해 자립 지원 (Claude Frontier Academy 12주 과정 등) |

자체 개발 역량이 있는 기업이라도 내부 데이터 구조와 승인 절차에는 밝지만 특정 모델의 한계나 에이전트 평가 방법, 공급자 플랫폼의 제약에는 익숙하지 않은 경우가 많다. 내부팀이 문제 정의부터 데이터 연결, 평가, 운영까지 모두 스스로 해낼 역량과 여력이 있다면 외부 FDE를 상시 배치할 필요가 없다. 모델 평가나 초기 구축 경험이 부족하다면, 그 단계를 외부 FDE와 함께 수행하며 전문성을 보충할 수 있다. 개발 조직이 있는 고객사에서 FDE를 활용하는 목적은 내부팀에 부족한 AI 적용과 평가 방법을 전수해, 스스로 시스템을 운영하도록 돕는 데 있다.

## 가장 흥미로운 지점

15개 문답을 읽으며 내가 가장 눈여겨본 대목은 FDE 조직의 확장성을 정하는 요인이다. 확장성은 현장에서 맞춤 코드를 얼마나 빠르게 짜느냐보다, 엔지니어의 반복 작업을 얼마나 체계적으로 줄이느냐에 좌우된다. 데카곤의 사례가 이를 보여준다. 데카곤은 약 스물다섯 번째 고객의 CRM을 연동할 무렵에야 셀프서비스 설정 기능을 만들었고, 판촉 규칙 변경도 자연어 설정 도구로 전환해 에이전트당 맞춤 개발 작업을 80% 줄였다. 현장 경험 없이 처음부터 범용 플랫폼을 설계하려 들면 고객이 가져온 47쪽짜리 대시보드 명세를 그대로 구현하거나 정작 현장에서는 쓰기 어려운 복잡한 설정 화면을 만들기 쉽다. 반대로 엔지니어가 현장에서 스물다섯 번 직접 연동 코드를 짜며 고객마다 달라지는 조건과 반복되는 절차를 확인한 뒤에 추상화하면, 무엇을 공통 설정으로 만들고 무엇을 개별 코드로 남길지 명확히 판단할 수 있다.

OpenAI와 앤트로픽, AWS가 모델 성능 경쟁을 벌이는 와중에 일제히 FDE 조직과 교육에 1억 달러에서 수십억 달러를 투입하는 이유도 이 맥락에서 이해된다. 현장의 레거시 데이터와 승인 절차를 연결하고 예외를 처리해 본 경험은 데모 영상을 일상 업무 시스템으로 바꾸는 필수 조건이다. 동시에 일본 영업팀 슬라이드 도구 사례처럼 모델의 사후학습과 플랫폼의 다음 기능을 결정하는 가장 정확한 입력 데이터가 된다.
