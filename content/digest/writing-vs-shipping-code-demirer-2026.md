## 3줄 요약

1. NBER 워킹 페이퍼 35275. Demirer(MIT), Musolff(Wharton), Yang(MIT) 세 경제학자가 100,000명 이상의 GitHub 개발자 활동 데이터와 Microsoft 내부 텔레메트리를 결합하여 자동완성·sync 에이전트·async 에이전트 세 세대의 AI 코딩 도구가 미친 생산성 효과를 매칭 이벤트 스터디로 추정한다.
2. 주간 커밋 기준 누적 효과는 세대별로 +40%, +140%, +180%로 가파르게 커지지만, 같은 도구가 생산 계층(라인 → 파일 → 커밋 → PR → 저장소 → 릴리스)을 따라 위로 갈수록 효과가 감쇠한다. sync 에이전트의 경우 라인 +741%가 PR +65%, 릴리스 +20%까지 압축된다.
3. CES 생산함수에 맞춰 보정한 AI와 사람 노동 사이의 대체탄력성은 약 0.25 — 강한 보완성을 가리킨다. 4대 앱 마켓플레이스에서도 새 앱 출시는 가속됐으나 첫 3개월 누적 사용량은 정체. 거시 성장 문헌의 "weak links" 논리를 단일 생산 공정 내부로 적용한 첫 실증이다.

## 분석 설계 — 같은 개발자의 1년 전 활동과 비교한다

저자들은 단순한 cross-section 대신 **matched event study**를 쓴다. 어떤 개발자가 AI 코딩 도구를 채택한 주를 이벤트 0주로 잡고, 그 개발자가 채택 직전 12주 동안 보였던 활동 수준과 *정확히 1년 전 같은 활동 수준을 보인 대조군 개발자*를 짝지운다. 이렇게 1년 전 대조군을 쓰는 이유는 두 가지다.

- **현재 대조군 오염**: 같은 시점의 비채택자도 AI를 쓰고 있을 가능성이 높다. 공개 저장소에서 흔적이 남지 않은 사용자가 많다.
- **부정적 선택 회피**: 같은 해의 비채택자는 활동성이 낮은 개발자로 쏠릴 수 있다. 1년 전 대조군은 채택 풀에서 끌어오기 때문에 이 편향이 줄어든다.

추적하는 도구는 6종이다.

- **Autocomplete**: GitHub Copilot (2022년 6월 출시)
- **Sync 에이전트**: GitHub Copilot Sync, Claude Code, OpenAI Codex (Sync 모드)
- **Async 에이전트**: GitHub Async Agent (2025년 5월), OpenAI Codex Async

플라시보로 비-AI 도구인 GitHub Pro 구독과 Docker 도입도 같은 디자인으로 측정한다 — 활동성 편향(activity bias)이 결과를 만든 게 아닌지 가르기 위해서다.

## 생산 계층을 6단계로 분해한다

이 페이퍼의 개념적 출발점은 소프트웨어 산출을 *수직 계층*으로 본다는 것이다. 한 줄을 작성하는 데 드는 노력이 모여 파일이 되고, 파일이 모여 커밋이 되고, 커밋이 모여 PR이 되고, PR이 모여 저장소가 되고, 저장소가 모여 릴리스가 된다.

| 계층 _s_ | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 단위 | Lines of Code | Files | Commits | Pull Requests | Projects | Releases |

각 계층은 상위 단계 입력(_y_<sub>s-1</sub>)과 그 계층의 effective input(_e_<sub>s</sub>, 사람 노력 + AI 산출 합)을 CES 생산함수로 결합한다. 핵심 파라미터는 두 단계 사이의 *대체탄력성* σ다. σ가 1보다 작을수록 상위 산출과 그 위 단계 사람 노력은 보완재 — 한쪽만 풍부해져도 다른 쪽 병목이 가로막아 산출이 제한된다. 이것이 Kremer(1993)의 O-ring, Jones(2011)의 weak-link 논리를 단일 생산 공정 안으로 가져온 형태다.

AI 도구는 이 사다리에 두 가지 방식으로 개입한다.

- **Augmentation**(증강): 그 계층 사람 노력의 단위당 생산성을 높인다. autocomplete가 코드 작성층(s=1)에 하는 일.
- **Partial automation**(부분 자동화): 그 계층 사람 노력을 부분적으로 대체하지만, 상위 layer의 사람 검토는 여전히 필요하다. sync·async 에이전트가 커밋·PR 층에서 하는 일.

## 세대별 task-level 생산성 — autocomplete +40%, +sync +140%, +async +180%

![Figure 5: Productivity Effects of GenAI Coding Tools](/images/writing-vs-shipping-code-demirer-2026/fig5-productivity-by-generation.png)
*각 세대 도구가 주간 커밋 수에 미친 효과. (a) Copilot autocomplete 2022년 코호트, (c) sync 에이전트 풀, (e) async 에이전트의 agent-authored commit. 우측 열은 채택 전 활동 분위별 효과. — NBER WP 35275, Figure 5.*

각 세대의 21\~30주 시점 효과는 분명하다.

- **Autocomplete**: 주간 커밋 +36%. 2022년 Copilot 채택자 기준. 채택 전 활동이 가장 낮은 1사분위는 +85%, 가장 높은 4사분위는 +21%. 모든 분위에서 양의 효과를 유지한다.
- **Sync 에이전트**: 사람 작성 커밋 기준 +109%. autocomplete의 약 3배다. Claude Code가 +199%로 가장 크고, OpenAI Codex(sync) +94%, GitHub Sync +43% 순. 도구별 차이는 도구 자체의 성능 차이와 *어떤 개발자가 그 도구를 채택했는지*의 선택 효과가 섞여 있다.
- **Async 에이전트**: agent-authored 커밋 기준 +34%. 이는 사람 커밋 위에 덧붙는 효과다. 채택 전 활동이 낮은 사분위에서 +105%, 가장 높은 사분위에서 +7%로, 활동량 분포 전 구간에서 효과를 보인다.

세 효과를 누적하면 채택자의 주간 커밋은 평균적으로 약 2.8배까지 늘어난다. 채택 후 30주까지 안정적으로 유지된다.

### 비-AI 플라시보는 5주 안에 사라진다

활동성 편향이 아닌지를 확인하기 위해 두 비-AI 도구를 같은 디자인으로 돌렸다.

- **GitHub Pro 구독** (비-AI 유료 구독, 순수 플라시보): 채택 직후 +137% 급등 → 5주 안에 0%로 수렴
- **Docker 도입** (그 자체로 생산성을 올릴 수 있는 도구, 상한선 역할): 채택 직후 +413% 급등 → 23%에서 안정

반면 AI 도구의 sync 효과는 30주 내내 109% 수준에서 유지된다. 단발성 활동 spike가 아니다.

### Claude Code의 효과는 학습이 아니라 모델 업데이트가 끌어올린다

Sync 에이전트는 이벤트 시간에 따라 효과가 *증가*하는 패턴을 보인다. 두 가지 가설이 가능하다 — (a) 사용자가 도구 활용법을 학습하면서 효과가 누적되는 것, (b) 도구를 받치는 *프론티어 모델*이 그동안 개선된 것. 두 가설을 가르기 위해 저자들은 출시 직후 3주 안에 채택한 *조기 코호트*만 떼어냈다. 이 부분 표본에서는 이벤트 시간이 곧 캘린더 시간이라, 모델 출시일을 가로축에 직접 표시할 수 있다.

결과는 명확하다. Claude Code 효과는 Anthropic의 Opus 4 → 4.1 시기에 정체하다가 Opus 4.5가 프론티어로 자리잡자 가파르게 상승한다. 반면 2022년 채택자의 Copilot autocomplete는 초기 spike 이후 줄곧 평평하다 — 그 시기 모델이 거의 갱신되지 않았다는 사실과 일치한다. 즉 sync 에이전트의 장기 효과를 끌어올리는 것은 사용자의 학습이 아니라 그 아래에서 갈리는 모델이다.

## 생산 계층을 따라가는 감쇠 — 라인 +741%가 릴리스 +20%로 압축된다

![Figure 1: Overview of Productivity Effects of AI Coding Tools](/images/writing-vs-shipping-code-demirer-2026/fig1-overview.png)
*세 세대 AI 코딩 도구가 생산 계층 6단계에 미친 누적 효과(채택 후 평균 % 변화). — NBER WP 35275, Figure 1.*

이 페이퍼의 두 번째이자 핵심 기여는 같은 도구가 *위 계층으로 갈수록 효과가 얼마나 줄어드는지*를 추적한 데 있다. Table 5의 21\~30주 추정치를 보자.

| 도구 | Lines | Files | Commits | PRs | Repos | Releases |
|---|---|---|---|---|---|---|
| Autocomplete | +228.2% | +50.8% | +35.9% | +11.0% | +13.6% | +10.2% |
| Sync 효과 (풀) | +741.3% | +187.0% | +109.1% | +65.5% | +25.5% | +20.3% |
| Claude Code (sync) | +981.2% | +288.4% | +199.2% | +145.5% | +49.2% | +29.2% |
| GitHub Sync | +470.9% | +106.2% | +42.7% | +21.4% | +11.3% | +1.3% |
| Codex (sync) | +792.6% | +186.4% | +94.3% | +61.8% | +14.6% | +0.2% |
| Async 효과 (풀) | +658.3% | +52.4% | +33.6% | +71.8% | +13.8% | — |

여러 사실이 이 표 한 장에 모여 있다.

- **단조 감쇠**: autocomplete는 6단계를 따라 거의 단조감소한다. sync도 큰 틀에서 단조감소다.
- **첫 단계의 감쇠가 가장 가파르다**: 라인이 파일로 모일 때 vector가 절반 이하로 압축된다. 사람의 검토·통합 노력이 가장 먼저 깎는다.
- **Async는 PR 층에서 튀어오른다**: async 에이전트의 PR 효과(+71.8%)는 커밋 효과(+33.6%)보다 크다. 이는 async 도구가 PR 자체를 자율적으로 만들어 그 층에 *직접* 산출을 더하기 때문이다 — 모델 예측과 정확히 일치한다.
- **GitHub Sync, Codex sync의 릴리스 효과는 통계적으로 거의 0**: 정상 표준오차 안에 들어간다. 코드 작성 단계에서는 70배 이상 효과를 내는 도구가 출시 단계에서는 흔적이 사라진다.

### CES 보정 — 대체탄력성 σ ≈ 0.25

저자들은 autocomplete 추정치만으로 두 구조 파라미터 (θ, σ)를 보정한다. autocomplete가 코드 작성층에만 개입한다는 깨끗한 가정 덕분에 윗단계 효과는 모두 *pass-through* 공식으로 예측 가능하다. 최적합값은 θ ≈ 0.75, σ ≈ 0.25다.

- **θ ≈ 0.75**: 각 계층 산출에서 상위 입력의 출력 탄력성이 약 75%, 그 계층 사람 노력은 약 25%.
- **σ ≈ 0.25**: 1보다 한참 작다. 상위 산출과 그 위 단계 사람 노력은 강하게 보완재. 둘이 거의 고정 비율로 결합돼야 한다.

이 동일한 (θ, σ)를 sync·async 에이전트에 *반사실*로 적용한 그림 10이 흥미롭다. 두 에이전트가 *코드 작성층에만 개입했다면* 라인-PR 사이 효과가 어떻게 되었을지 예측한 곡선과, 실제 관측치를 겹쳐 본다. 결과는 — sync 에이전트의 파일·커밋·PR 효과가 모델 예측보다 약 2/3가 더 크다. async 에이전트는 PR 효과가 예측을 크게 상회한다. 두 패턴 모두 두 에이전트가 *상위 계층까지 직접 개입*하고 있음을 보여준다.

![Figure 8: Sync Effect Across Production Layers](/images/writing-vs-shipping-code-demirer-2026/fig8-attenuation-sync.png)
*Sync 에이전트 채택의 생산 계층 6단계별 이벤트 스터디. 라인 +741%에서 릴리스 +20%까지 단조 감쇠. — NBER WP 35275, Figure 8.*

## 마켓플레이스 — 새 앱은 늘었지만 사용량은 그대로다

![Figure 12: New Apps and Their Usage Across App Stores](/images/writing-vs-shipping-code-demirer-2026/fig12-app-marketplaces.png)
*4대 앱 마켓플레이스의 월별 새 앱 수(위), 코호트 누적 사용량(가운데), 소규모 사용자 도달 앱 비중 변화(아래). 음영 영역은 agentic coding era(2025년 2월\~). — NBER WP 35275, Figure 12.*

개발자 수준 결과가 산업 전체로 흘러갔는지 확인하기 위해 저자들은 4대 앱 마켓플레이스 데이터를 모았다 — Apple App Store(iOS), Google Play Store(Android), Chrome Web Store, SourceForge. 각 마켓플레이스에서 (a) 새 앱 출시 수와 (b) 출시 후 첫 3개월 누적 사용량을 추적한다.

### 새 앱 출시는 가속됐다

- **iOS**: 2023\~2025 초반 월 30,000\~50,000개에서, 2026년 4월 월 100,000개로 가속.
- **Android**: 2020년 중반 월 120,000개 → 2025년 1월 월 42,000개로 감소 추세였으나 2025년부터 안정·회복. 2026년 중반 월 60,000개.
- **Chrome 확장**: 2023년 월 5,000개 → 2026년 중반 월 13,000개로 약 2배. 가속 시점이 iOS보다 빨라 — autocomplete 시기부터 효과가 누적됐을 가능성.
- **SourceForge**: 변화 없음. AI 도구를 덜 쓰는 개발자 기반이 반영된다.

GitHub 공개 저장소 차원에서도 같은 패턴이 보인다. 월간 머지된 PR 수와 새 (비-fork) 저장소 수가 2025년 초부터 pre-2025 추세에서 명확하게 이탈한다. PR 가속이 새 저장소 가속보다 크다는 점도 — *생산 계층상 PR이 저장소보다 한 단계 아래라 더 큰 효과가 잡힌다*는 감쇠 패턴과 일치한다.

### 사용량은 그렇지 않다

문제는 그 다음이다. 각 월 코호트의 첫 3개월 누적 사용량(iOS = 평점 수, Android·Chrome = 다운로드 수)을 모두 더해도 평탄하거나 줄어든다. iOS 코호트 평점 합, Android 코호트 다운로드 합 모두 2024년과 2025년이 거의 같다. Chrome은 이미 감소 중이었다. 더 많은 앱이 나왔지만 그것이 사용량으로 옮겨지지 않는다.

저자들은 두 가설을 모두 검증한다.

- **롱테일 가설(소수 사용자×많은 앱)**: 누적 사용량이 평탄하니 기각. Amazon의 AI 책 출판에서는 관찰됐지만(Reimers and Waldfogel, 2026) 소프트웨어 마켓플레이스에서는 보이지 않는다.
- **매칭 개선 가설(니치 앱이 사용자에게 더 잘 맞춰진다)**: 출시 후 3개월 안에 *최소 사용자*에도 닿지 못한 앱 비중을 본다. iOS에서 평점 10개 미만 앱 비중이 79% → 86%, Chrome에서 다운로드 10개 미만이 18% → 31%로 상승. 매칭이 좋아진다면 이 비중은 떨어져야 한다. 결과는 반대다.

남은 해석은 두 가지다. 한계 앱들의 품질이 낮거나(공급 측), 사용자의 발견·채택이 추가 공급을 흡수할 만큼 빠르게 늘지 못하거나(수요 측). 데이터로 가르지 못한다. 다만 한 가지는 분명하다 — 코드 작성층의 생산성 폭증이 도달 사용량으로 자동 환산되지 않는다.

## 가장 눈여겨본 것 — 병목은 위로 이동하고 있다

이 페이퍼가 단순한 정량 추정으로 멈추지 않는 이유는 결론부의 한 문장에 있다. "the binding constraint appears to be shifting from writing code to reviewing, integrating, and ultimately distributing it." — 병목이 *코드 작성에서 검토·통합·배포로* 옮겨가고 있다.

이는 두 가지 함의를 가진다.

첫째, autocomplete는 작성층(s=1)에만 들어왔다. sync 에이전트는 s=1, 2(파일), 3(커밋)에 동시에 들어왔다. async 에이전트는 s=4(PR)에까지 진입했다. 도구가 진화하면서 *AI 개입이 깊어진다*. Figure 1에서 더 위 세대 도구일수록 *오른쪽 계층까지 효과가 살아남는 것*은 그 결과다.

둘째, 그럼에도 σ = 0.25는 그대로 남아 있다 — 각 계층의 사람 노력은 여전히 보완재로 작동한다. AI가 한 계층을 *부분 자동화*해도 그 위 계층에서 사람의 검토·결정이 필요하다. 그래서 매번 새 세대 도구가 등장할 때마다 효과가 *한 계층씩 위로 늘어나는* 패턴이 나타난다. 다시 말해 — 다음 병목은 PR 리뷰와 릴리스 결정이다. 이 단계까지 AI가 들어와 σ가 높아지면 다음 세대의 release 효과는 +20%보다 훨씬 클 수 있다.

이 모델은 또 하나의 관찰을 가능하게 한다. 사람들이 자주 갖는 의문 — "내가 AI로 코딩이 빨라졌는데 왜 출시는 그만큼 빨라지지 않는 걸까?" — 에 대한 *구조적 답*이 여기 있다. 라인 +741%가 PR +65%로 압축되는 데에는 자기 자신 개발자의 시간 배분 문제만이 아니라, *팀이라는 생산 사다리 전체의 보완성*이 작동하고 있기 때문이다. 한 사람의 코드 작성층 생산성이 7배가 되어도, 그 위에서 코드 리뷰·통합·릴리스를 담당하는 사람들의 처리량이 그대로면 출시 처리량은 그 비율 만큼 따라오지 않는다.

거시 성장 문헌의 약한 연결 가설(Kremer 1993, Jones 2011, 2026)이 보통 *작업 간*의 보완성을 가리켰다면, 이 페이퍼는 그것을 *단일 생산 공정의 수직 계층 내부*에 적용한 첫 실증이다. 같은 논리가 의료(진단 → 처치 → 처방), 법무(서면 작성 → 검토 → 제출), 콘텐츠(스크립트 → 편집 → 배포)에도 그대로 적용된다면, "AI로 X가 빨라졌으니 X가 만드는 산출도 빨라질 것"이라는 단순 외삽은 거의 항상 과대 추정일 것이다.

## 한계

저자들이 직접 밝힌 한계가 셋이다.

1. **소프트웨어 품질을 직접 측정하지 못한다.** 평점·다운로드 같은 간접 지표에 의존한다. 자유 앱의 사용자 가치를 평점이 정확히 반영하지 않을 수 있다.
2. **포착 범위가 일부다.** GitHub + 4개 마켓플레이스는 큰 단면이지만 기업 내부 소프트웨어·엔터프라이즈 소프트웨어는 빠진다.
3. **다른 도메인으로의 외삽이 보장되지 않는다.** 소프트웨어 개발은 현재 생성형 AI의 가장 앞선 응용 영역이다. 이 정량 추정치를 다른 도메인에 그대로 옮기긴 어렵다.

본 다이제스트 작성자 시점에서 더하자면, 본 추정의 외부 타당성에 대한 한 가지 추가 의문이 있다. 공개 저장소 활동만 본다는 점이다. 저자들이 11월 2025년 GitHub 내부 데이터로 비교한 결과, *공개 저장소 측정치는 async agent 사용자의 24.2%를 잡고, 이 사용자들의 활동량 중 72.9%를 포착*한다. 활동 측정치는 큰 그림에서 대표적이지만, 비공개 엔터프라이즈 환경의 AI 사용 패턴이 다를 가능성은 남는다.
