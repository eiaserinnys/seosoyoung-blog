## 3줄 요약

1. SpaceX(xAI)에서 Grok Bot을 개발하는 로렌 탄(Lauren Tan, `@poteto`)은 2026년 11월 AI Engineer Code Summit에서 팀의 개발 방식을 공개했다[^affil]. 이 팀은 한 달 동안 프로덕션에 풀 리퀘스트(PR) 11,000건을 배포하면서도 되돌림(revert) 비율을 약 0.5%로 유지했다.
2. 에이전트가 일관된 품질의 코드를 작성하게 하려면 마크다운 규칙 문서(`AGENTS.md`)를 늘리는 대신 코드베이스 자체에 결정론적 제약을 설계해야 한다. 실제로 이 팀은 제품 코드에서 React의 `useEffect`와 코드 주석의 99%를 금지하고, 이를 오류 원인을 안내하는 린트 규칙으로 대체했다.
3. 코드 리뷰는 코드 한 줄 한 줄을 읽는 작업에서 실행 영상, 상태 머신 다이어그램, TLA+와 Lean 정형 검증 결과 같은 검증 산출물을 확인하는 절차로 전환됐으며, 일일 토큰 사용량의 약 70%가 이 검증 과정에 투입된다.

[^affil]: 유튜브 영상 제목과 설명란에는 소속이 `SpaceXSI`로 표기돼 있으나, AI Engineer Code Summit 2026 공식 세션 소개 페이지에는 `SpaceXAI`로 적혀 있고 발표 슬라이드 우측 상단에는 `SPACEX` 로고와 `Grok Bot` 로고가 함께 표시된다.

## 에이전트 시대의 엔지니어링 과제와 신뢰의 역피라미드

로렌 탄은 발표 직전 한 달 동안 혼자서 프로덕션에 PR 3,000건을 배포했다. 에이전트가 등장하기 전에는 주말 사이에 구글 지도를 새로 개발한 브렛 테일러(Bret Taylor) 같은 극소수 예외를 빼면 코드 생산량 자체를 핵심 지표로 삼는 일이 드물었다. 이제는 에이전트를 통해 누구나 대량의 코드를 쏟아낼 수 있으므로, 소프트웨어 엔지니어의 본질적인 과제는 생산량을 크게 늘리면서도 코드 품질을 유지하거나 개선하는 구조를 설계하는 일로 바뀌었다.

로렌 탄은 이 체계를 흔히 쓰이는 '소프트웨어 팩토리(software factory)'라는 용어 대신 '신뢰(trust)'의 문제로 정의한다. 에이전트를 맹목적으로 믿기보다, 따로 지시하지 않아도 올바른 코드를 작성할 수밖에 없는 실행 환경을 구축해 신뢰를 확보한다. 잠든 사이에도 수천 건의 PR을 배포할 수 있는 환경을 구축하기까지 로렌 탄은 6개월을 들였다.

에이전트 환경에 시간을 투자하는 우선순위는 '포테토 피라미드(The Poteto Pyramid)'라 부르는 역피라미드 구조로 정리된다. 위쪽 영역일수록 결과가 결정론적이고 투자 대비 효과가 크며, 아래쪽 영역으로 갈수록 실행 비용과 불확실성이 커진다.

| 단계 (위에서 아래 순서) | 성격 | 핵심 구성 요소 | 에이전트 환경에서의 역할과 비용 특성 |
| :--- | :--- | :--- | :--- |
| **1. 코드베이스 (Codebase)** | 결정론적 | 좋은 API 설계, 아키텍처, 리팩토링 | 에이전트에 입력되는 가장 큰 맥락. 잘못된 사용 자체를 원천 차단하며 유지 비용이 가장 낮음 |
| **2. 정적 분석 (Static Analysis)** | 결정론적 | 린트 규칙, 타입 시스템, 컴파일러, 테스트, CI | 코드베이스 설계와 결합해 에이전트의 행동 범위를 제약하고 올바른 구현을 강제함 |
| **3. 검증 (Verification)** | 검증 산출물 기반 | 런타임 검증(CDP, 피처 맵), 정형 검증(TLA+, Lean), 속성 기반 UI 테스트(Bombadil) | 시스템 불변성을 검증하고 버그를 검출하며, 에이전트가 사용자의 의도와 목표를 제대로 이해했는지 확인함 |
| **4. 산문 지침 (Prose)** | 확률적 판단 | 규칙 문서(rules), 스킬(skills), `AGENTS.md` | 결정론적 수단으로 처리할 수 없는 판단 영역에만 최소한으로 사용함 |

2024년만 해도 엔지니어가 하루에 검토하는 동료의 PR은 3건 안팎이었으나, 현재는 엔지니어 한 명이 수백 개에서 수천 개의 에이전트를 운용하며 하루 300건 규모의 PR을 다룬다. 에이전트는 입력을 바탕으로 출력을 생성하는데, 가장 큰 입력이 바로 기존 코드베이스다. 다음 에이전트는 코드베이스에 남은 임시방편(workaround), 안티패턴, 폐기 예정 코드, 기술 부채를 팀의 표준 패턴으로 간주하고 그대로 복제한다. 정원에 잡초나 해충이 한 번 생기면 순식간에 번지는 현상과 같다. 이 때문에 에이전트를 교정할 때마다 `AGENTS.md`에 문장을 덧붙이기보다, 교정 내용을 코드베이스 수정과 정적 분석 규칙으로 구현하는 정원 가꾸기(gardening)가 선행되어야 한다.

![단정한 정원 화단에서 한 손으로 엉킨 가시 잡초를 뽑아내고 다른 손으로 반듯한 새싹 줄 옆에 하늘색 규칙 표지말뚝을 세우는 치비 서소영](https://img.seosoyoung.eiaserinnys.me/images/poteto-all-code-is-slop/chibi-02-garden-lint.png)

## Dune 프레임워크와 강제 가능한 아키텍처

Grok Bot 팀은 이처럼 코드베이스를 정갈하게 가꾸는 유기적 아키텍처(organic architecture) 철학을 구현하기 위해 **Dune**이라는 자체 클라이언트 프레임워크를 만들었다. 구조상으로는 Electron 데스크톱 애플리케이션용 Next.js에 가깝다. 데스크톱 앱을 개발하며 겪은 실패 사례들을 엄격한 제약과 린트 규칙으로 프레임워크 안에 내재화했다.

```
"세심한 맥락 판단이 필요한 기능은 자주 저품질 코드(slop)를 낳는다."
```

대표적인 사례가 React의 `useEffect`다. `useEffect`는 유효한 사용처가 있지만 숙련된 개발자조차 오용하기 쉬우며, 에이전트 역시 이를 제대로 다루지 못한다. Grok Bot 팀은 제품 코드(product code)에서 `useEffect` 사용을 전면 금지하고, Dune 프레임워크 내부의 특정 API 구현체에서만 제한적으로 허용했다. 그 결과 `useEffect` 오용으로 발생하는 버그 유형이 통째로 사라졌고, 코드 리뷰에서 이를 확인할 필요도 없어졌다.

디렉토리 구조를 통해 에이전트에 맥락을 강제하는 방식도 함께 사용한다. Electron 기반 에디터인 Cursor를 개발할 당시 에이전트들이 메인 스레드(main thread) 코드를 렌더러 스레드(renderer thread)로 자주 불러와 긴 블로킹 작업과 화면 끊김(jank)을 유발하는 문제가 반복됐다. Grok Bot과 Dune에서는 최상위 디렉토리 두 개에 아예 `electron-renderer`와 `electron-main`이라는 직관적인 이름을 붙이고, 의존성 그래프 분석기와 린트 규칙으로 두 디렉토리 사이의 교차 임포트를 금지했다. 설정은 간단하지만 코드 리뷰에서 신경 써야 할 항목을 영구적으로 하나씩 줄여 준다.

| 구분 | 기존 에이전트 운용에서 나타난 문제 | Grok Bot 및 Dune의 결정론적 해결책 |
| :--- | :--- | :--- |
| **React 부수효과 처리** | 에이전트가 `useEffect`의 미묘한 생명주기 조건을 다루지 못해 버그 양산 | 제품 코드에서 `useEffect` 전면 금지, Dune 내부 API로만 캡슐화 |
| **스레드 간 모듈 참조** | Electron 렌더러 스레드에 메인 스레드 코드를 임포트해 UI 끊김 유발 | `electron-renderer`와 `electron-main` 최상위 폴더 분리 및 교차 임포트 린트 차단 |
| **비동기 타이머와 주석** | 아키텍처 충돌을 `setTimeout` 등으로 때우며 주석에 변명을 작성해 전역 확산 | 코드 주석 99% 금지, 근본 원인 수정을 안내하는 상세 린트 에러 메시지로 대체 |

## 코드 주석의 99% 금지와 린트 에러 메시지 활용

로렌 탄은 에이전트를 운용하며 마크다운 문서, 규칙 파일, 코드 주석이 <strong>"올바른 해결책을 택하지 않은 이유를 변명하는 공간"</strong>으로 쓰인다는 현상을 발견했다. 또한 에이전트가 사람이 지나가듯 지적한 사소한 교정 사항에 과도하게 집착해, 이를 절대 규칙처럼 문서에 적어 두는 일도 잦았다.

Cursor 개발 과정에서 겪은 명령형 타이머 남발 사례가 이 문제를 잘 보여 준다. 당시 코드베이스에는 VS Code의 명령형(imperative) 아키텍처와 React의 선언형(declarative) 아키텍처가 충돌하는 지점이 있었다. 에이전트들은 근본적인 구조 충돌을 해결하기 어려우니 `setTimeout`, `requestAnimationFrame`, `requestIdleCallback` 같은 명령형 타이머를 임시방편으로 즐겨 사용했다. 자바스크립트에서 수많은 타이머가 짧은 주기로 생성되었다가 해제되면 대규모 가비지 컬렉션(GC)이 발생해 심각한 지연과 화면 끊김이 일어난다. 설상가상으로 에이전트는 타이머를 호출하는 코드마다 이 임시방편이 불가피하다는 긴 주석을 달아 두었고, 뒤에 투입된 에이전트들은 그 주석과 타이머 코드를 앱 전체에 그대로 베껴 썼다.

이 교훈을 바탕으로 Grok Bot 팀은 **코드 주석의 99%를 금지**했다. 주석은 금방 낡고, 사람도 에이전트가 작성한 장황한 주석을 읽지 않으며, 무엇보다 강제력이 없다. 다음 에이전트에게 특정 패턴을 쓰지 말라고 주석으로 남겨 봐야 지켜진다는 보장이 없다. 대신 Grok Bot과 Dune에서는 안티패턴이 감지되면 임시방편에 기대지 말고 근본 원인을 고치도록 해결 방법을 안내하는 린트 에러 메시지를 반환한다. 에이전트를 교정할 때마다 결정론적 검사나 API 개선으로 남기는 작업이 누적되면 코드 리뷰에서 지적할 항목이 점차 줄어들고, 결국 에이전트가 대부분의 PR을 스스로 병합한다.

## 런타임 검증, 정형 검증, 그리고 토큰의 70%가 쓰이는 곳

코드베이스와 정적 분석으로 기본 품질을 확보한 뒤에는 에이전트의 자율성과 신뢰도를 높이기 위해 검증(verification)을 결합한다. 현재 Grok Bot 팀의 코드 리뷰는 코드 텍스트를 읽는 대신 실행 영상, 스크린샷, 상태 다이어그램, 정형 검증 증명서 같은 <strong>검증 산출물(verification artifacts)</strong>을 확인하는 과정으로 전환됐다.

![낮은 돌담 가드레일 옆에서 원시 코드 두루마리 묶음은 바닥에 내려놓고 하늘색 검증 스탬프를 든 채 상태 머신 다이어그램과 실행 영상을 확인하는 치비 서소영](https://img.seosoyoung.eiaserinnys.me/images/poteto-all-code-is-slop/chibi-01-proof-review.png)

첫 번째 검증 도구는 <strong>런타임 검증(runtime verification)</strong>으로, 에이전트가 자신이 작성한 코드를 직접 실행하고 인간 개발자처럼 Chrome DevTools Protocol(CDP) 같은 디버깅 도구를 조작한다. Grok Bot 팀은 런타임 검증 스킬 내부에 <strong>피처 맵(feature map)</strong>을 구축했다. 사용자 관점에서 애플리케이션의 모든 기능을 정리한 사이트맵으로, 사람이 "왼쪽 사이드바에 있는 그 기능"이라고 모호하게 말하지 않아도 에이전트와 약속된 어휘로 정확히 소통할 수 있게 해 준다. 또한 스킬 안에 테스트 가능한 전용 CLI와 드라이버를 함께 만들어 두어, 에이전트가 매번 검증 스크립트를 새로 짜지 않고 재사용하도록 해 토큰 소모를 줄였다.

두 번째는 최근 도입해 효과를 보고 있는 <strong>정형 검증(formal verification)</strong>과 <strong>속성 기반 UI 테스트(property-based UI testing)</strong>다.

| 검증 도구 및 스킬 | 적용 영역 | 구체적인 검증 대상과 효과 |
| :--- | :--- | :--- |
| **TLA+** | 상태 모델 체킹 | 여러 기기와 플랫폼에 걸친 알림 동기화 등 주요 사용자 흐름의 상태 전이 검증 |
| **Lean** | 알고리즘 수학적 증명 | 자체 제작한 UI 가상화(virtualization) 라이브러리에서 화면 깜빡임이나 떨림이 없음을 증명 |
| **Bombadil** | 속성 기반 UI 테스트 | 무작위 상태와 입력 조합에서 UI 불변성을 검사해 다수의 UI 버그 사전 검출 |
| **`pstack`의 `statechart`** | 상태 머신 시각화 | 사용자 관점의 상태 머신을 다이어그램으로 생성해 실행 영상 및 스크린샷과 대조 검수 |

로렌 탄은 엔지니어 신디(Cindy)의 X 게시물을 인용하며 검증의 비중을 강조했다. 신디는 6개월 전만 해도 미묘한 버그가 병합되는 문제 때문에 에이전트를 신뢰하지 못했으나, 검증 체계를 갖춘 뒤로는 **일일 토큰 사용량의 70%를 검증에 투입**하고 있다고 밝혔다. 로렌 탄의 토큰 사용 비중도 이와 일치한다. 정적 분석, TLA+, Lean, 속성 기반 테스트는 모두 기존 소프트웨어 엔지니어링에 존재하던 기법이지만, 과거에는 사람이 명세와 테스트를 직접 작성하고 유지보수하는 데 드는 비용이 너무 커 널리 쓰이지 못했다. 이제는 에이전트가 그 작성과 유지보수 비용을 크게 낮추면서, 모든 요소를 경제적으로 검증할 수 있는 소프트웨어 테스팅과 검증의 황금기가 시작됐다고 로렌 탄은 진단했다.

## 한 달 11,000건 PR의 성과와 자동화 루프의 전제 조건

이러한 환경 투자에 힘입은 Grok Bot 팀의 2026년 10월 한 달간 운영 지표와 기여자 구성은 다음과 같다[^chart].

| 지표 구분 | 2026년 10월 실적 | 세부 내용 |
| :--- | :--- | :--- |
| **팀 월간 PR 배포 수** | **11,000건** | 프로덕션 브랜치에 실제 병합 및 배포된 풀 리퀘스트 기준 (로렌 탄 개인 3,000건 포함) |
| **안정 버전 릴리스 주기** | **일 1회** | 데스크톱 클라이언트 안정(stable) 빌드를 하루 한 번꼴로 배포 |
| **PR 되돌림(Revert) 비율** | **약 0.5%** | 배포 속도가 빨라지는 동안에도 되돌림 비율은 줄어들어 0.5% 수준을 유지함 |
| **월간 기여자 수 (총 227명)** | 코어 23명 / 캐주얼 및 단발 204명 | 1,000건 이상 1명(코어), 100\~999건 22명(코어), 10\~99건 77명(캐주얼), 2\~9건 78명(단발), 1건 49명(단발) |
| **클라이언트 체감 성능** | 출시 시점 대비 모든 지표 개선 | Electron 앱의 한계에도 앱 시작, 타이핑, 새 채팅 열기, 채팅 전환 속도가 모두 초기보다 빨라짐 |

[^chart]: 10월 월간 기여자 수의 구간별 인원은 발표 슬라이드의 막대그래프 수치를 기준으로 정리했다. 전체 월간 기여자 수는 2026년 8월 11일 출시 이후 9월 163명, 10월 227명으로 늘었다.

맥락을 깊이 알지 못하는 단발성(drive-by) 기여자 수백 명이 동시에 코드를 보태고 하루 수백 건의 PR이 병합된다. 단단하게 설계된 내부 코딩 루프(inner coding loop)의 제약이 이 규모의 동시 작업에서도 코드 품질을 지탱한다. 로렌 탄은 처음부터 모든 것을 자동화하는 '소프트웨어 팩토리(외부 루프)' 구축부터 서두르지 말라고 권고한다. 내부 코딩 루프가 저품질 코드를 만들어 내는 상태에서 외부 자동화만 가동하면 토큰만 더 쓰고 저품질 코드를 대량 생산할 뿐이다.

반대로 코드베이스 개선, 안티패턴 방지 린트 규칙 신설, 기존 레거시 패턴 정리, 런타임 및 정형 검증 체계가 먼저 갖춰지면 외부 자동화 루프(outer loop)는 자연스럽게 구축된다. 현재 Grok Bot 팀에서는 새 릴리스를 배포할 때마다 Grok Bot이 자동으로 Cursor 클라우드 에이전트 프로젝트를 실행한다. 이 에이전트는 실제 사용자처럼 애플리케이션 전체 빌드를 조작하며 퍼징(fuzzing) 테스트를 수행한다. 에이전트는 버그를 발견하면 스스로 수정 PR을 생성하고, 사람이 일일이 깊이 검토하지 않아도 <strong>자동 병합(auto-merge)</strong>까지 마친다. 코드베이스의 제약 장치가 생성되는 PR의 기본 품질을 이미 보장하고 있으므로 사람 손을 거치지 않는 병합이 성립한다.

## 가장 흥미로운 지점

발표에서 특히 시선을 끈 대목은 에이전트가 코드 주석과 마크다운 문서를 '태만과 임시방편을 합리화하는 도피처'로 쓴다는 관찰이었다. 흔히 에이전트가 잘못된 코드를 짜면 개발자는 `AGENTS.md`에 주의사항을 한 줄 더 적거나 코드 옆에 주석으로 이유를 남기려 한다. 하지만 에이전트에게 자연어 주석은 강제력이 없는 참고 문장에 불과하다. 까다로운 아키텍처 문제를 정면으로 풀지 않고 `setTimeout` 한 줄로 임시 처리한 뒤, "레거시 타이밍 이슈 때문에 불가피함"이라는 그럴듯한 변명을 적어 넣는 수단이 될 뿐이다. 더구나 다음에 투입된 에이전트는 그 변명 주석이 달린 임시방편을 프로젝트의 공인된 해법으로 학습해 코드베이스 전역에 복제한다.

| 비교 항목 | 산문 지침과 주석 중심 접근 | Grok Bot 팀의 결정론적 환경 접근 |
| :--- | :--- | :--- |
| **오류 교정 수단** | `AGENTS.md`에 주의사항 추가, 코드 주석으로 경고 작성 | 문제 API(`useEffect` 등) 금지, 해결법을 담은 린트 규칙 추가 |
| **에이전트의 반응** | 주석에 우회 사유를 변명으로 적고 `setTimeout` 등 임시방편 복제 | 컴파일 및 린트 단계에서 차단되어 근본 원인을 수정하도록 강제됨 |
| **인간 엔지니어의 역할** | 매일 수백 건의 코드 한 줄 한 줄과 주석을 직접 읽으며 사후 적발 | 실행 영상, `statechart` 다이어그램, 정형 검증 산출물 중심으로 검수 |

주석의 99%를 금지하고 모든 교정을 린트 규칙과 API 제약으로만 남기겠다는 결정은 극단적으로 보이지만, 에이전트가 맥락을 소비하는 방식을 정확히 꿰뚫은 처방이다. 일일 토큰의 70%를 코드 생성보다 TLA+, Lean, 런타임 검증에 투입한다는 수치도 같은 관점으로 설명된다. 에이전트 시대에 엔지니어링 품질을 지키는 일은 프롬프트를 정교하게 작성하는 작업에서, 잘못된 코드가 컴파일과 린트 및 검증 단계를 통과하지 못하도록 결정론적 환경을 설계하는 작업으로 전환되고 있다.
