## 3줄 요약

1. 2026년 11월 NVIDIA Research의 Peter Belcak, Pavlo Molchanov 등 연구진 12명이 논문을 발표했다. 현대 언어 모델의 20만\~100만 토큰급 컨텍스트 윈도우가 실제 과제를 푸는 데 꼭 필요한지 검증한 연구다.
2. 13개 벤치마크 실험에는 두 가지 기법이 쓰였다. 대화 이력이 일정 길이에 도달할 때마다 핵심 작업 상태만 추려 새 대화를 시작하는 대화 말미 압축(EoCC)과, 입력 문서를 파일시스템에 두고 필요한 부분만 골라 읽는 선택적 입력 읽기다. 그 결과 Claude Opus 4.5와 GPT 5.6 Sol은 활성 컨텍스트를 16K\~48K 토큰으로 유지하면서도 기존 전체 컨텍스트 방식과 대등한 정확도를 유지했고, 장문 독해와 검색 벤치마크에서는 최대 40.0%p 높은 성적을 기록했다.
3. 나아가 환경에 행동을 한 번 실행할 때마다 대화를 초기화하고 자연어 상태만 갱신하는 단일 행동 압축(SAC)에서도 SWE-bench Verified와 Terminal-Bench 2.1의 성능이 유지되는 것을 확인했다. 이 결과를 바탕으로 자연어 상태를 주고받도록 사후 학습하는 의미 상태 공간 모델(SSSM)을 제안한다.

## 1. 긴 컨텍스트의 비용 구조와 세 가지 연구 질문

언어 모델이 토큰 하나를 생성하는 데 드는 연산량과 메모리 사용량은 입력 컨텍스트에 누적된 토큰 수에 비례해 증가한다[^1]. 상용 API는 입력 컨텍스트 길이와 무관하게 토큰 100만 개당 고정 요금을 부과하므로 최종 사용자는 길이에 따른 비용 차이를 체감하기 어렵다. 그러나 클라우드 GPU에서 모델을 직접 서빙할 때 컨텍스트 윈도우 크기는 처리량과 직결된다.

[^1]: 트랜스포머 디코딩 단계에서 새 토큰 하나를 생성할 때마다 기존 입력 토큰 전체의 KV 캐시를 참조해야 하므로 연산 비용이 컨텍스트 길이에 선형으로 비례한다. 컨텍스트를 처음부터 채우는 프리필(prefill) 단계까지 포함하면 시퀀스 길이의 제곱에 비례하는 비용이 든다.

컨텍스트 윈도우 크기가 실제 디코딩 처리량에 미치는 영향을 확인하기 위해 오픈웨이트 코딩 모델 3종의 최대 지속 처리량을 크기별로 실측했다. 실험 환경은 vLLM 엔진으로 구동하는 NVIDIA H100 GPU 클러스터이며, 비용은 시간당 3.85달러(2026년 9월 Nebius 온디맨드 단가 기준)로 계산했다. 설정한 컨텍스트 윈도우 크기를 16K 토큰에서 256K 토큰으로 늘리면, 동일한 하드웨어에서 출력 토큰 100만 개를 생성하는 데 드는 비용은 GLM 5.2가 3.6배, Kimi K2.6이 5.6배, Qwen 3 Coder Next가 7.0배로 늘어난다. 거꾸로 16K로 줄였을 때의 비용 절감 폭은 4비트 양자화나 구조적 희소화(sparsification) 같은 모델 경량화 기법으로 얻는 효율 개선과 맞먹거나 그보다 크다.

| 모델 (서빙 구성) | 16K 대비 256K 비용 |
|---|---|
| GLM 5.2 (INT4, H100 16기) | 3.6배 |
| Kimi K2.6 (INT4/FP8, H100 16기) | 5.6배 |
| Qwen 3 Coder Next (BF16, H100 8기) | 7.0배 |

컨텍스트가 256K 토큰에 가까워지면 다수 모델에서 토큰 간 지연 시간이 처음의 약 2배로 늘어난다. MiniMax M2.7(GGUF IQ3\_XXS)은 전체 파라미터가 230B이고 활성 파라미터가 10B인 모델인데, 컨텍스트 길이가 약 64K 토큰을 초과하면 가용 메모리 한도인 109GB를 모두 쓰고 실행이 중단된다.

짧은 컨텍스트로 얻는 비용과 속도의 이점이 이렇게 뚜렷한데도, 현재 주류 언어 모델의 컨텍스트 윈도우는 고전 문학 단행본 한 권의 분량을 훨씬 초과하는 규모로 커졌다.

논문은 실제 워크로드에서 컨텍스트가 길어지는 원인을 두 가지로 구분한다. 첫째는 **장기 실행 과제**(long-horizon task)다. 에이전트가 환경을 관찰하고 행동하기를 반복하는 동안 명령, 도구 출력, 중간 판단이 대화에 계속 누적된다. 둘째는 **장문 입력 과제**(long-input task)다. 질문에 답하려면 읽어야 하는 원문 자체가 수십만 토큰에 이른다. 장문 입력을 파일시스템에 파일로 저장해 두고 모델에 선택적 읽기 도구를 주면, 장문 입력 과제는 장기 실행 과제로 바꿔 풀 수 있다. 이 구분에서 논문이 답하려는 세 가지 연구 질문이 도출된다.

1. 장기 실행 과제를 긴 컨텍스트 없이 완수할 수 있는가?
2. 장문 입력 과제를 긴 컨텍스트 없이 완수할 수 있는가?
3. 컨텍스트 하나당 최대 한 번의 행동만 수행하면서도 장기 실행 과제를 완수할 수 있는가?

## 2. 실험 방법론: 세 가지 컨텍스트 관리 방식과 압축 구조

소프트웨어 엔지니어링과 터미널 과제에는 공개된 `mini-swe-agent` v2.4 하네스를 사용했다. 나머지 과제인 정보 탐색, 도구 사용, 장문 독해에는 `mini-swe-agent`를 일반화한 `mini-agent` 하네스를 썼다. 두 하네스 모두 한 턴에 하나의 Bash 명령을 실행하고 표준 출력과 종료 코드를 돌려받는 최소한의 ReAct 루프로 동작한다. 실험에서는 이 기본 하네스에 세 가지 컨텍스트 관리 방식을 적용해 비교했다.

![전체 이력 누적(FHA), 대화 말미 압축(EoCC), 단일 행동 압축(SAC) 세 가지 컨텍스트 관리 방식의 대화 흐름 비교 도식](https://img.seosoyoung.eiaserinnys.me/images/you-dont-need-long-context/fig3-context-regimes.png)
*그림 3: 본 연구가 비교한 세 가지 컨텍스트 관리 방식. 전체 이력 누적(FHA)은 단일 대화에 모든 행동을 누적하고, 대화 말미 압축(EoCC)은 임계치 도달 시 상태를 요약해 새 대화를 시작하며, 단일 행동 압축(SAC)은 매 행동 직후 상태를 갱신하고 대화를 초기화한다. (출처: Belcak et al., 2026)*

1. **전체 이력 누적(FHA, Full-History Accumulation)**: 에이전트의 모든 행동과 환경 관찰 결과를 작업이 끝날 때까지 단일 대화에 계속 덧붙이는 기본 방식이다.
2. **대화 말미 압축(EoCC, End-of-Conversation Compaction)**: 활성 대화의 토큰 길이가 미리 정한 압축 임계치(compaction threshold)에 도달하면, 모델에 현재 작업 상태를 정리한 인계 문서(handoff recap)를 작성하도록 지시한다. 그 직후 기존 대화를 폐기하고 시스템 프롬프트, 원래 과제 설명, 압축된 상태 문서만 포함한 새 대화를 시작해 작업을 이어간다. 설정값은 `전체 컨텍스트 한도 / 압축 임계치`(예: `32K / 24K`)로 표기하며, 두 값의 차이는 압축 턴을 생성하는 데 쓰는 여유분이다.
3. **단일 행동 압축(SAC, Single-Action Compaction)**: 대화 이력을 전혀 누적하지 않고 압축된 의미 상태(semantic state)만 유지한다. 매 대화에서 모델은 과제와 현재 의미 상태를 입력받아 환경에 행동을 정확히 한 번 수행하고, 그 결과를 반영해 의미 상태를 갱신한 뒤 대화를 끝낸다.

부록 A와 G는 **정확도를 보존하는 압축의 조건**을 자세히 밝힌다. 흔히 컨텍스트 압축을 단순한 대화 요약(summarization)으로 취급하기 쉽지만, 일반 요약은 입력에 나온 모든 정보를 똑같은 비중으로 다루고 같은 내용이 되풀이되는 실행 로그에도 지나치게 많은 분량을 할애하는 경향이 있다. 이와 달리 정확도를 가장 잘 보존한 압축은 과거 실행 이력의 줄거리를 재구성하는 대신 **앞으로 수행할 작업에 필요한 핵심 근거만 선별해 적은 실행 인계서** 형태를 띠었다. 모든 워크로드에 공통으로 쓴 압축 프롬프트는 다음 다섯 항목을 반드시 기록하게 한다.

| 압축 인계서 필수 항목 | 기록 내용 | 목적 |
|---|---|---|
| 1. 과제 목표와 원본 요구사항 | 입력 과제의 원문(또는 거의 그대로인 사본)과 한 줄 목표 | 반복 압축 과정에서 초기 제약 조건과 사용자 의도가 유실되는 현상 방지 |
| 2. 확인된 근거와 정확한 경로 | 파일 경로, 심볼명, 실행 명령, 관측된 수치, 주요 오류 메시지 | 검증된 관측 결과와 아직 확인하지 않은 가설을 엄격히 분리 |
| 3. 적용된 변경과 검증 상태 | 수정하거나 생성한 파일 목록, 변경 내용, 테스트 통과 여부 | 이미 완료한 수정 작업을 새 대화에서 중복 수행하는 낭비 차단 |
| 4. 막다른 길(Dead ends) | 시도했으나 실패해 다시 반복하지 말아야 할 접근법 | 이전 대화에서 실패한 풀이를 새 대화가 되풀이하는 루프 방지 |
| 5. 남은 계획과 다음 행동 | 실행 순서대로 정리한 하위 목표, 직후 실행할 명령, 완료 판정 기준 | 새 대화의 첫 턴이 탐색 지연 없이 즉시 다음 행동을 이어받도록 유도 |

평가에는 프론티어 모델인 **Claude Opus 4.5**(기준 윈도우 200K 토큰)와 **GPT 5.6 Sol**(표준 요금 상한 272K 토큰, 최대 1.05M 토큰)을 주력 모델로 썼다. 보조 실험에는 DGX Spark에 배치한 오픈웨이트 모델 5종(Qwen 3.6 27B, Qwen 3 Coder Next 80B-A3B, Gemma 4 31B, Step 3.7 Flash 198B-A11B, MiniMax M2.7 230B-A10B)을 썼다.

## 3. 장기 실행 과제: 짧은 컨텍스트에서도 유지되는 정확도

첫 번째 연구 질문(장기 실행 과제를 긴 컨텍스트 없이 해결할 수 있는가)을 검증하려고 6개 장기 실행 벤치마크에서 EoCC의 컨텍스트 한도를 단계적으로 낮추며 FHA 베이스라인과 비교했다. 소프트웨어 엔지니어링과 터미널 영역에서는 실제 GitHub 이슈 해결을 다루는 **SWE-bench Verified**(500문항), 9개 프로그래밍 언어를 아우르는 **SWE-bench Multilingual**(300문항), 샌드박스 컨테이너에서 터미널 과제를 해결하는 **Terminal-Bench 2.1**(89문항)을 시험했다. 정보 탐색과 도구 사용 영역에서는 위키피디아 문서 2\~15개를 조합해 다단계 추론을 수행하는 **FRAMES**(824문항), 소매, 항공, 통신 도메인의 정책 아래 가상 사용자와 대화하며 도구를 호출하는 **$\tau^2$-bench**(184문항), 다중 턴 도구 호출을 평가하는 **BFCLv3**(장문 에피소드 200문항)를 함께 평가했다.

컨텍스트 한도를 16K\~48K(벤치마크에 따라 최저 8K)로 크게 낮춘 조건에서도 두 모델의 정확도는 베이스라인 수준을 유지하거나 한층 높아졌다. 6개 벤치마크에서 시험한 22개 임계치 설정 가운데 베이스라인보다 정확도가 2%p를 초과해 떨어진 설정은 두 모델 각각 5개 이하였다. Claude Opus 4.5는 베이스라인과의 정확도 차이가 3.7%p 하락에서 5.6%p 상승 사이였고, 추정 최적화 소매 비용(EORC)[^2]은 2.2배에서 8.8배까지 줄었다. GPT 5.6 Sol은 정확도 차이가 3.3%p 하락에서 4.4%p 상승 사이였고, 비용은 2.4배에서 5.0배 절감됐다.

[^2]: 저자들은 부록 B에서 짧은 컨텍스트 전용 서버를 운영할 때의 비용 절감 효과를 추산하려고 **추정 최적화 소매 비용(EORC, Estimated Optimized Retail Cost)** 지표를 정의했다. EORC는 컨텍스트 한도 $W$가 기준 윈도우(Opus 4.5는 200K, GPT 5.6 Sol은 272K)에서 16K로 줄어들 때 출력 토큰 단가가 표준 요금(Opus는 100만 토큰당 25달러, GPT는 100만 토큰당 20달러)의 20%까지 선형으로 낮아진다고 보간한 값이다. 이 20%는 그림 4에서 실측한 오픈웨이트 3종의 256K 대비 16K 비용 비율(0.2772, 0.1777, 0.1439)의 평균값 $r = 0.20$이다. 신규 입력과 캐시 적중 입력 단가도 출력 대 신규 입력 단가 비율(5:1)과 신규 입력 대 캐시 적중 입력 단가 비율(10:1)을 그대로 유지해 합산한다.

압축을 자주 하면 에이전트가 이전 작업을 잊어버리고 같은 파일을 반복해서 조회하느라 토큰 소비량이 급증할 것이라는 우려가 흔하다. 그러나 부록 C의 토큰 소비 내역을 보면, 컨텍스트 한도를 줄일 때 프롬프트 캐시 재사용 토큰이 줄고 신규 입력 토큰과 압축 출력 토큰이 소폭 늘었을 뿐 전체 작업 길이는 크게 달라지지 않았다. 특히 Claude Opus 4.5는 SWE-bench Verified의 `24K / 18K` 설정에서 정확도가 70.0%에서 74.8%로 4.8%p 올랐다. 컨텍스트 단가 할인을 반영하지 않은 명목 API 비용(Nominal retail cost)도 420.00달러에서 295.75달러로 줄었다. 이는 불필요하게 긴 과거 시행착오 로그가 제거되어 모델이 현재 단계의 문제 해결에 더 잘 집중했기 때문이다.

부록 D에서 평가한 로컬 오픈웨이트 모델 5종은 출력 습관이 모델마다 달라서 압축의 영향도 제각각이었다. **Qwen 3.6 27B**와 **MiniMax M2.7**은 압축을 위한 별도의 사후 학습 없이도 `32K / 24K` 설정에서 SWE-bench Verified 베이스라인 수준을 유지했다. 베이스라인은 각각 68.6%와 72.6%, 압축 설정은 68.2%와 73.2%였다. Terminal-Bench 2.1에서도 `16K / 12K`까지 베이스라인 성적을 보존했다. 반면 **Qwen 3 Coder Next**는 한 턴에 지나치게 장황하게 추론하고 출력하는 경향이 있다. 그 때문에 `16K / 12K` 설정에서는 압축 주기마다 의미 있는 진전을 이루지 못했고, SWE-bench Verified 정확도가 53.0%에서 3.6%로 급락했다.

한편 논문 3.1절은 손실 압축(lossy compression)인 EoCC만으로 해결할 수 없는 예외 상황도 함께 다룬다. 예를 들어 에이전트가 동전 던지기 도구를 수백 번 호출한 뒤에 $i$번째 던지기 결과를 조회해야 하는 과제라면, 고정된 크기의 압축 인계서는 언젠가 개별 시행 기록을 잃어버릴 수밖에 없다. 이 경우 하네스가 전체 대화 로그를 환경의 파일로 기록해 두고 에이전트가 선택적 읽기 도구로 필요한 시점의 로그만 검색하게 구성하면, 과거 대화 조회는 다음 절에서 다루는 장문 입력 과제로 전환된다. 다시 말해 과거 대화 기록에 간헐적으로 접근해야 하는 요구사항이 곧 그 기록 전체를 매 턴 모델의 활성 컨텍스트에 유지해야 하는 이유가 되지는 않는다.

## 4. 장문 입력 과제: 문서를 통째로 넣는 방식보다 선택적 읽기가 나은 이유

두 번째 연구 질문(장문 입력 과제를 긴 컨텍스트 없이 해결할 수 있는가)을 검증하려고 7개 장문 독해 및 검색 벤치마크에서 실험을 진행했다. 실제 업무에 가까운 장문 질의응답 과제로는 8K\~2M 단어 규모의 단일 문서와 다중 문서를 다루는 **LongBench v2**(503문항), 영어와 중국어 재무 보고서, 판례, 학술 논문 여러 편에 분포한 근거를 종합하게 하는 **LOONG**(1,600문항), 평균 약 100K 토큰 규모의 실무 문서 묶음 7개 범주를 추론하게 하는 **AA-LCR**(100문항)을 포함했다. 인위적으로 구성한 바늘 찾기(needle-style) 과제로는 16K\~500K 토큰 문서에서 특정 문장을 찾는 **NIAH**(125문항)와 256K 및 500K 토큰에서 다중 바늘 검색, 변수 추적, 다단계 질의응답 등 13개 과제를 수행하는 **RULER**를 시험했다. 이와 함께 4K\~128K 토큰 문서 곳곳에 별표(★)와 함께 삽입된 32개의 숫자를 수집하고 정정된 값을 가려내는 **Counting-Stars**(192문항), 64K\~1M 토큰 소설 텍스트에 삽입된 명제들을 연결해 추론하는 **BABILong**(550문항)을 평가했다.

베이스라인은 긴 문서 전체를 프롬프트에 통째로 넣어 모델에 전달한다. 반면 `mini-agent` 하네스는 문서를 환경의 파일시스템에 텍스트 파일(`input01.txt`, `doc02.txt` 등)로 저장하고, 초기 프롬프트에는 질문과 파일 목록만 제공한다. 에이전트는 부록 E에 정의된 도구를 조합해 필요한 대목만 골라 읽는다.

| 도구명 | 명령 동작 및 제한 | 실제 활용 사례 (부록 E.2 기록 로그) |
|---|---|---|
| **docs-list** | 파일 목록과 바이트, 줄 수, 문자 수 조회 (**doc-stats** 병행) | LOONG 및 AA-LCR에서 다중 문서의 분량과 파일 구조를 파악 |
| **grep** | 정규식 일치 줄 번호 검색 (`head`, `sed`와 조합) | LongBench v2의 100만 자 칼라망어 문법서에서 `kademor`가 등장하는 3840번 줄 식별 |
| **doc-syn** | 검색어의 동의어 및 표기 변형 확장 | 어휘가 정확히 일치하지 않는 문항에서 후보 검색어 집합 생성 |
| **doc-read** | 문자 오프셋이나 줄 범위 지정 독해 (기본 6,000자, 최대 8,000자) | 칼라망어 문법서 3835\~3870번 줄(36줄)이나 AA-LCR 보고서 245\~272번 줄(28줄)만 정밀 독해 |

부록 E.2의 실제 실행 로그를 보면 이 방식이 어떻게 작동하는지 알 수 있다. LongBench v2의 첫 번째 문항에서 에이전트는 약 100만 자(18,830줄) 분량의 칼라망어(Kalamang) 문법서를 참조해 문장을 번역해야 했다. 에이전트는 문법서 전문을 컨텍스트에 넣지 않았다. 대신 `grep -n -i -E '\bkademor\b'` 명령으로 그 동사가 등장하는 3840번 줄을 찾아내고, `doc-read --lines 3835:3870`으로 주변 36줄의 문법 설명과 예문만 읽어 답을 도출했다. AA-LCR의 한 문항은 30년간 소비자법 위반 건수가 많았던 산업의 순위를 구하되 방송업은 제외하라고 요구했다(40만 4천 자 분량의 보고서 4편). 이 문항에서도 에이전트는 `grep`으로 위반 건수가 언급된 줄을 찾은 뒤 `doc-read --lines 245:272`로 28줄만 읽어 항공업(12건), 방송업(단일 기업 10건, 제외 대상), 숙박업(4건)의 위반 건수와 제외 조건을 정확히 파악했다.

| NIAH | GPT 5.6 Sol | 80.0% ($56.00) | 48K: 100.0% ($0.24) | +20.0%p (233.3배) |
| RULER | Opus 4.5 | 62.5% ($880.00) | 16K: 95.7% ($20.57) | +33.2%p (42.8배) |
| RULER | GPT 5.6 Sol | 65.5% ($725.60) | 16K: 96.4% ($9.02) | +30.9%p (80.5배) |

수십만 토큰짜리 문서를 프롬프트에 통째로 넣으면 관련 없는 방대한 텍스트에 어텐션이 분산되어 추론 정확도가 떨어진다. 반면 선택적 읽기를 쓰면 모델은 핵심 단서가 있는 문단만 골라 읽는다. 그 결과 Opus 4.5의 정확도는 AA-LCR에서는 65.0%에서 84.0%로, BABILong에서는 67.1%에서 92.0%로 급등했다. 문서 전체를 프리필하지 않고 필요한 구간만 읽기 때문에 비용도 낮아졌다. 컨텍스트 단가 할인을 가정하지 않은 현재의 상용 API 명목 요금으로 따져도 Opus 기준 LOONG은 1,367.50달러에서 497.75달러, RULER는 880.00달러에서 102.85달러, BABILong은 360.50달러에서 57.20달러로 줄었다.

문서가 아무리 길어져도 에이전트가 문제를 푸는 데 실제로 쓰는 대화 토큰의 총량은 일정한 수준에서 더 늘지 않는다는 것을 그림 7과 그림 8이 보여 준다. 문서 길이가 $10^4$토큰(1만)에서 $10^6$토큰(100만) 이상으로 수백 배 길어질 때 문서 전문을 입력하는 $y=x$ 점선은 기하급수적으로 치솟지만, 선택적 읽기 에이전트의 총 대화 길이는 LongBench v2에서 대부분 10K\~40K 토큰이다. 압축이 일어난 횟수의 중앙값도 대부분 0회였다. 예외는 LongBench v2의 Opus 4.5와 LOONG `16K / 12K`의 Opus 4.5로, 중앙값이 둘 다 1회였다. 다시 말해 대부분의 장문 입력 과제는 압축 임계치에 한 번도 도달하지 않고 몇 차례의 정밀 검색과 부분 읽기만으로 해결된다.

## 5. 매 행동마다 대화를 초기화하는 단일 행동 압축(SAC)과 SSSM

세 번째 연구 질문은 압축 빈도를 가장 높인 경우를 묻는다. 대화 말미에만 압축하는 대신 환경 행동(Bash 명령)을 한 번 실행할 때마다 상태를 압축하고 대화를 즉시 폐기하는 단일 행동 압축(SAC)을 쓰면 에이전트의 성능은 어떻게 될까? 연구진은 `mini-swe-agent`에 SAC를 적용해 SWE-bench Verified와 Terminal-Bench 2.1을 평가했다.

| 모델 | 벤치마크 | FHA 베이스라인 정확도 (피크 길이 중앙값/최댓값) | 최고 EoCC 정확도 (피크 길이 중앙값/최댓값) | SAC 정확도 (피크 길이 중앙값/최댓값) |
|---|---|---|---|---|
| Claude Opus 4.5 | SWE-bench Verified | 70.0% (32K / 200K) | 74.8% (19K / 22K) | 70.2% (8K / 16K) |
| Claude Opus 4.5 | Terminal-Bench 2.1 | 47.2% (27K / 130K) | 52.8% (24K / 31K) | 51.8% (9K / 19K) |
| GPT 5.6 Sol | SWE-bench Verified | 84.4% (18K / 173K) | 88.8% (22K / 35K) | 82.4% (7K / 15K) |
| GPT 5.6 Sol | Terminal-Bench 2.1 | 87.6% (17K / 133K) | 88.8% (23K / 40K) | 84.3% (8K / 37K) |

매 행동마다 이전 대화 기록을 완전히 지우고 압축된 의미 상태만 다음 턴으로 넘겼는데도 Claude Opus 4.5는 SWE-bench Verified에서 70.2%로 베이스라인(70.0%)과 같은 수준이었고, Terminal-Bench 2.1에서는 51.8%로 베이스라인(47.2%)보다 4.6%p 높았다. GPT 5.6 Sol은 SWE-bench Verified 82.4%, Terminal-Bench 2.1 84.3%로 베이스라인보다 각각 2.0%p, 3.3%p 근소하게 낮았다(84.3%는 89문항 중 75문항을 푼 결과다). 과제마다 활성 컨텍스트가 가장 길어졌을 때의 길이를 피크 길이라 하면, 그 중앙값은 두 모델 모두 **7K\~9K 토큰**에 불과했다. 가장 긴 피크도 기존의 130K\~200K 토큰에서 15K\~37K 토큰으로 대폭 줄었다.

논문 5.1절은 이 단일 행동 압축 결과를 확장해 **의미 상태 공간 모델**(SSSM, Semantic State Space Model)이라는 새로운 모델 패러다임을 제시한다. 오늘날의 프론티어 모델은 단일 행동 압축을 따로 학습하지 않았는데도 7K\~9K 토큰의 짧은 컨텍스트만으로 복잡한 소프트웨어 엔지니어링 과제를 해결할 수 있다. 그렇다면 처음부터 모델을 이 단일 행동 루프에 맞춰 사후 학습(post-training)할 수 있다는 것이 연구진의 논리다. 이들이 정의하는 SSSM은 한 번의 추론 호출에서 다음 다섯 단계를 수행하도록 훈련된 모델이다.

1. 입력으로 주어진 자연어로 적힌 대화 상태 설명(semantic state)을 이해한다.
2. 현재 과제와 상태를 바탕으로 다음에 취할 적절한 행동을 추론한다.
3. 환경에서 단일 행동을 실행한다.
4. 행동의 실행 결과를 확인하고 기록한다.
5. 추론한 내용, 행동 결정, 실행 결과를 반영해 자연어 상태 설명을 갱신함으로써, 별도의 SSSM 추론 인스턴스가 다음 턴의 작업을 온전히 이어받을 수 있게 한다.

| 비교 항목 | 전체 이력 누적 모델 (기존 LLM) | 상태 공간 모델 (SSM) | 의미 상태 공간 모델 (SSSM) |
|---|---|---|---|
| 턴 간 상태 표현 | 이전 대화와 도구 호출 이력 전문을 KV 캐시에 누적 | 신경망 내부의 블랙박스 연속 벡터 상태 유지 | 사람이 읽고 검증할 수 있는 자연어 의미 상태 갱신 |
| 추론 시 컨텍스트 크기 | 작업이 길어질수록 수십만 토큰으로 계속 증가 | 고정 크기 상태이나 자연어 수준의 상태 점검 불가 | 매 행동마다 초기화되어 피크 중앙값 7K\~9K(최대 15K\~37K) 유지 |
| 사후 학습 및 서빙 효율 | 긴 문맥 내 어텐션 대상 구간 학습 필요, 큰 KV 캐시 비용 발생 | 순환 상태 학습 필요 | 과거 문맥 어텐션 학습 부담이 적고 짧은 윈도우로 고속 서빙 |

SSSM은 순환 신경망 계열의 상태 공간 모델(SSM, State-Space Model)과 개념적으로 닮았지만 차이가 있다. 기존 SSM은 토큰을 생성하는 사이사이에 사람이 해석할 수 없는 블랙박스 신경망 벡터 상태를 유지한다. SSSM은 대화 턴 사이에 **사람이 읽고 검증하고 수정할 수 있는 자연어 의미 상태**를 유지한다. 연구진은 SSSM이 짧은 컨텍스트로 서빙되므로 클라우드 추론 비용을 낮추고 로컬 추론 속도를 크게 높일 것으로 전망한다. 또 수십만 토큰의 과거 문맥 가운데 어디에 주목해야 하는지 가르칠 필요가 없어 학습 데이터 효율도 훨씬 높을 것이라고 본다[^3].

[^3]: 저자들은 결론(논문 6절)에서 이 연구의 실험 결과가 긴 컨텍스트가 유리한 과제의 존재 가능성을 완전히 배제하지는 못한다고 밝힌다. 모든 과제가 짧은 컨텍스트로 풀린다는 것을 수학적으로 증명하지도 않는다고 덧붙인다. 그럼에도 튜링 기계로 정의되는 계산 가능성(computability)은 본래 한 번에 유한하고 제한된 입력만 읽고 유한한 내부 상태를 갱신하며 임의의 계산을 수행하는 것을 전제로 한다. 저자들은 이와 같은 이치로, 긴 입력과 오래 이어지는 작업을 이유로 거대 컨텍스트 윈도우가 필수라고 여겨 온 통념이 실험에서는 성립하지 않았다고 강조한다.

## 가장 흥미로운 지점

부록 A와 G에서 일반 대화 요약(summarization)과 실행 인계(handoff compaction)를 다른 작업으로 분리해 정의한 분석이 이 논문의 핵심을 이룬다. 이 구분을 매 행동 단위까지 적용한 결과가 SSSM이다. 에이전트 개발자 다수가 컨텍스트 압축을 도입했다가 모델이 이전 지시를 잊거나 같은 실수를 되풀이하는 일을 겪었다. 논문은 그러한 성능 저하가 짧은 컨텍스트 한도 때문이 아니었음을 보여주며, 과거의 실행 궤적을 똑같은 비중의 줄거리로 요약하게 만든 프롬프트 설계에서 원인을 찾는다. 줄거리 대신 앞으로 필요한 정보(요구사항, 검증된 근거, 완료된 수정, 실패한 경로, 다음 명령)만 구조화해 넘기면, Bash 명령 한 번마다 대화를 초기화하는 SAC 환경(피크 컨텍스트 중앙값 7K\~9K 토큰)에서도 SWE-bench Verified 정확도가 70\~82%로 유지된다.

| 기존 장문 컨텍스트 관행 | 본 논문이 제시한 짧은 컨텍스트 해법 | 실험 결과 및 제안 요지 |
|---|---|---|
| 과거 실행 궤적 전체를 균등한 줄거리로 요약 | 원본 요구사항, 확인된 경로, 실패 경로, 다음 명령 중심의 실행 인계서 | 16K\~48K 한도와 단일 행동 압축(SAC)에서도 SWE-bench 정확도 유지 |
| 수십만 토큰 원천 문서를 프롬프트에 일괄 입력 | 문서를 파일시스템에 두고 `grep`과 `doc-read`로 필요한 구간만 독해 | 장문 벤치마크 정확도 최대 +40.0%p 향상, EORC 4.4\~233.3배 절감 |
| 200K\~1M 토큰 컨텍스트 윈도우 기반 모델 서빙 | 자연어 의미 상태를 매 행동마다 갱신하도록 사후 학습하는 SSSM 제안 | 256K 대신 16K 윈도우로 서빙할 때 출력 토큰 생성 비용 3.6\~7.0배 절감 |

NIAH와 RULER를 비롯한 7개 장문 입력 벤치마크에서는 문서를 프롬프트에 넣지 않고 파일시스템에 두어 `grep`과 `doc-read`로 읽게 했다. 그러자 대다수 벤치마크에서 정확도가 4.6\~40.0%p씩 올랐고 압축 횟수의 중앙값은 0회였다. 이 결과는 무엇을 '모델의 기억'에 넣고 무엇을 '외부 환경의 도구'로 다뤄야 하는지 기준을 제시한다. 수십만 토큰을 KV 캐시에 계속 유지하는 거대 컨텍스트 윈도우 경쟁보다, 16K 안팎의 짧은 활성 컨텍스트에서 자연어 상태 갱신과 선택적 파일 탐색을 수행하도록 모델과 하네스를 함께 설계하는 편이 비용, 지연 시간, 정확도에서 모두 낫다는 것을 이 논문은 숫자로 보여 준다.
