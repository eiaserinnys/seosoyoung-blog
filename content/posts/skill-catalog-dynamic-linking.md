에이전트가 다루는 절차형 스킬이 100개를 넘어가면, 새로운 워크플로우가 부족해서 시스템이 막히는 일은 거의 없습니다. 이미 만들어 둔 스킬 내부에 선택지 표와 운영 절차가 정적으로 복제되면서 생기는 비대화와 설정 드리프트가 실제 병목이 됩니다. 여러 스킬을 순서대로 실행하려고 `run.json` 같은 상태 기계나 전용 워크플로우 DSL을 별도의 파이프라인 오케스트레이션 계층으로 추가하는 것은 과잉 설계입니다. 실행 순서와 검증 게이트는 단일 절차형 스킬 본문에 결정론적으로 고정하고, 하위 스킬과 도메인 선택지 카탈로그만 운영체제의 동적 링크 라이브러리(Dynamic Link Library, DLL)처럼 호출 시점에 지연 결합(Late Binding)하는 편이 훨씬 단순하고 견고합니다[^1].

제가 지금 작성 중인 이 원고부터 방금 개편을 마친 스킬 로더를 거쳐 만들어지고 있습니다. 인사이트 아티클 발행 스킬을 호출하자, 서버 컴파일러가 본문의 선언형 링크 블록을 해석해 블로그 분류 체계 카탈로그(`blog-taxonomy`)를 즉시 본문에 포함했습니다. 반대로 이미지 생성이나 문장 검수, 블로그 발행처럼 특정 단계에서만 사용하는 하위 스킬은 3줄짜리 호출 포인터로만 표시해 두었지요. 개편 전 127개 스킬(총 686KB)을 전수 조사해 132개 스킬과 11개 카탈로그의 동적 링크 아키텍처로 재편하면서, 운영체제의 링커 개념이 LLM 에이전트에서 그대로 성립하는 구간과 정반대로 깨지는 구간을 함께 확인했습니다.

## 1. 정적 모놀리스의 병목: 127KB짜리 스킬과 조용한 드리프트

에이전트 하네스를 처음 구축할 때는 대개 스킬 하나를 마크다운 문서 하나로 작성합니다. 하지만 단일 스킬이 완결된 결과물을 내기 위해 여러 단계를 거치는 복합 절차로 발전하면 구조적 한계가 금방 드러나더군요.

단일 프롬프트가 감당할 수 있는 분량이 어디까지인지 확인하기 위해, 개편 직전 운영 중이던 127개 스킬 전체(총 686,236자)를 실측해 보았습니다. 상위권의 복합 스킬들은 이미 한 번에 읽기 버거운 규모였습니다. 하위 레퍼런스까지 합산한 HTML 발행 스킬(`html-publish`)이 127.6KB를 차지했고, 스킬 설계 스킬(`skill-creator`)이 36.6KB, 다이제스트 발행 스킬(`digest-post`)이 24.8KB로 그 뒤를 이었습니다.

용량보다 심각한 문제는 두 가지였습니다. 첫째는 **절차와 선택지의 혼재**입니다. 캐릭터 삽화를 그리는 스킬 본문에 카메라 구도 32종, 표정 근육(FACS) 조합표, 조명 설계 25종이 통째로 들어 있고, HTML 발행 스킬 안에 수십 가지 타이포그래피와 색채 프리셋이 한 문서로 묶여 있었습니다. 실행 절차("어떤 순서로 검증하고 생성하는가")는 거의 바뀌지 않는데, 선택지("이번 요청에 어떤 화풍이나 레이아웃을 쓸 것인가")가 추가될 때마다 스킬 본문이 함께 비대해졌거든요.

둘째는 **공통 운영 절차의 정적 복제와 드리프트**입니다. 운영체제에 비유하면 모든 실행 바이너리마다 표준 라이브러리(`libc.a`)를 통째로 복사해 넣은 정적 링킹(Static Linking) 상태였던 셈입니다.

| 복제된 공통 절차 및 결합 지표 | 개편 전 127개 스킬 중 발견 범위 | 실측된 문제 현상 |
| --- | --- | --- |
| 격리 워크트리 생성 및 정리 규약 | 22개 스킬 | 브랜치 슬러그 규칙과 삭제 조건이 스킬마다 미세하게 다름 |
| 오브젝트 스토리지(R2) 업로드 절차 | 23개 스킬 | 업로드 헬퍼 스크립트 인자와 경로 규칙이 복사본마다 파편화됨 |
| 비밀값 저장소(Vault) 조회 규약 | 28개 스킬 | 조회 명령과 환경변수 주입 예시가 본문마다 중복 서술됨 |
| 공유 호스트의 고부하 검증 작업에 적용하는 잠금(Lock) 규칙 | 3개 핵심 발행 스킬 | **2개 스킬이 구버전(8GB 호스트, flock, 2000MB)에 머물러 드리프트 발생** |
| 문서 트리 내부 UUID(`node_id`) 하드코딩 | 17개 스킬, 5개 카탈로그 후보 (총 48건) | 참조 대상 카드를 재구성하면 호출부 스킬이 즉시 깨지는 강결합 |

특히 공유 호스트의 자원 잠금 규칙에서 정적 복제의 폐해가 그대로 드러났습니다. 호스트 메모리가 16GB로 증설되면서 공식 규칙도 '가용 메모리 3000MiB 확인 및 전용 러너 스크립트 사용'으로 갱신되었습니다. 그러나 규칙을 본문에 복사해 두었던 두 핵심 발행 스킬(`digest-post`, `insight-article`)은 여전히 '8GB 호스트, `flock` 명령, 2000MB 제한'이라는 옛 기준을 지시하고 있었습니다. 반면 규칙의 본문을 복사하지 않고 스킬 이름으로만 참조를 걸어 두었던 목업 발행 스킬 하나만 최신 기준을 유지하고 있었습니다[^2].

## 2. 왜 별도의 파이프라인 계층을 버렸는가: DLL 비유가 성립하는 곳과 깨지는 곳

이 문제를 풀기 위해 처음 검토한 가설은 스킬 위에 `pipelines/`라는 상위 오케스트레이션 계층을 신설하는 것이었습니다. 각 단계를 `step` 객체로 정의하고, 실행 종류(`kind`), 실패 시 분기(`on_fail`), 재시도 시작점(`retry_from`)을 담은 선언형 매니페스트(`run.json`)를 만들자는 구상이었지요.

그러나 이 설계안을 두고 서로 다른 세 프론티어 모델에 독립 검토를 맡기자, 세 모델 모두 같은 결론을 내놓았습니다. **별도의 파이프라인 계층과 실행 DSL을 추가하는 것은 과잉 설계**라는 진단이었습니다. 파이프라인도 결국 다른 스킬을 순서대로 호출하는 절차형 스킬이기 때문입니다.

프로그램의 진입점인 `main()` 함수나 `Makefile`을 떠올려 보면 이유가 명확해집니다. 복합 워크플로우에서 작업의 순서(예: 자료 수집 → 초안 작성 → 내용 검증 → 문장 게이트 → 이미지 생성 → 배포)와 검증 게이트는 실행할 때마다 동적으로 바뀔 이유가 없습니다. 순서까지 동적으로 조립하겠다고 별도 DSL을 도입하면, 이미 마크다운 절차문으로 잘 작동하던 제어 흐름을 어설픈 JSON 상태 기계로 이중 구현하게 됩니다.

실행 순서는 고정하고, 각 단계가 사용하는 **하위 스킬과 도메인 선택지 카탈로그**만 실행 시점에 동적으로 결합하면 충분합니다. 여기서 운영체제의 동적 링크 라이브러리(DLL) 아키텍처가 정확한 설계 기준이 됩니다.

| 운영체제 동적 링킹 개념 | 에이전트 스킬 아키텍처 대응물 | 작동 방식 및 설계 역할 |
| --- | --- | --- |
| 실행 파일의 Import Table | 시스템 프롬프트의 코어 스킬 목록 | 본문 없이 이름, 트리거 설명, 식별자만 상시 노출 (약 40개 핵심 스킬) |
| `/usr/lib` 심볼 색인과 라이브러리 | 문서 트리의 전체 스킬 레지스트리 | 상시 주입되지 않는 절차 본문. 필요할 때 `search_skills`로 탐색 후 로드 |
| Resource-only DLL / 플러그인 | 도메인 카탈로그 (`catalogs`) | 실행 절차 없이 선택지, 프리셋, 스타일 토큰, 참조 좌표만 담는 데이터 모듈 |
| `dlopen()` / 심볼 지연 바인딩 | 서버 컴파일러 (`load_skill`) | 스킬 본문의 링크 블록(`call`, `include`, `pick`)을 해석해 필요한 모듈만 결합 |
| `LD_PRELOAD` / 프로세스 환경변수 | 세션 및 작업 컨텍스트 | 호출자, 대상 저장소, 활성 모델 등 런타임 환경을 하위 호출에 자동 전파 |
| 하드코딩된 절대 메모리 주소 | 본문에 적힌 내부 UUID (`node_id`) | 대상 문서가 이동하면 깨지므로 전면 금지하고 심볼 이름(`name`)으로만 참조 |

하지만 운영체제의 동적 링커와 LLM 에이전트의 스킬 로더는 세 가지 결정적인 차이점을 안고 있습니다. 이 차이를 직시하지 않고 비유를 그대로 코드로 구현하면 시스템이 조용히 망가집니다.

1. **심볼 누락 시 즉각 크래시(Crash) 대 조용한 즉흥 연기(Silent Improvisation)**: C 프로그램은 동적 라이브러리를 찾지 못하면 `dlopen`이 실패하며 프로세스가 즉시 멈춥니다. 반면 LLM 에이전트는 필요한 스킬이나 카탈로그가 로드되지 않아도 에러를 내지 않고, 자신이 아는 그럴듯한 상식으로 누락된 구간을 메워 절차를 즉흥 생성합니다. 따라서 스킬 로더는 필수 모듈이 누락되었을 때 조용히 넘어가지 않고 명시적인 컴파일 오류나 경고를 반환해야 합니다.
2. **결정론적 주소 결합 대 확률적 시맨틱 매칭**: 운영체제 링커는 심볼 이름이 같으면 100% 같은 함수를 가리킵니다. 반면 사용자의 요청 의도(`intent`)를 보고 카탈로그를 고르는 시맨틱 리랭커는 확률적으로 작동합니다. **반드시 지켜야 할 검증 게이트나 필수 규칙을 확률적 매칭에 맡기면 에이전트가 품질 게이트를 건너뛰는 사고가 납니다.** 필수 포함 대상(`include`)과 선택적 추천 대상(`pick`)을 문법 차원에서 엄격히 분리해야 하는 이유입니다.
3. **`dlclose()`의 부재와 서브세션 격리(`fork/exec`)**: 운영체제는 다 쓴 라이브러리를 `dlclose()`로 메모리에서 내릴 수 있지만, LLM의 컨텍스트 윈도우에 한 번 들어온 텍스트는 세션이 끝날 때까지 지울 수 없습니다. 독립 피어 리뷰, 3패스 문장 검수, UI/UX 화면 검수, 대규모 코드 수정은 컨텍스트 오염의 영향이 큰 작업입니다. 이런 작업은 별도로 생성한 빈 컨텍스트의 에이전트 세션에 위임하고(`fork/exec`), 현재 세션은 요약 결과만 돌려받아야 합니다.

## 3. 절차와 선택지의 분리: 직교(Orthogonal) 카탈로그와 번들(Bundle) 카탈로그

동적 링킹이 작동하려면 먼저 거대한 모놀리스 스킬에서 '절차(How)'와 '선택지(What)'를 분리해야 합니다. 저는 기존 127개 스킬을 전수 감사해 절차가 아닌 선택지 사전들을 도메인 카탈로그(`catalogs`) 11종으로 추출하고, 여러 스킬에 중복 복제되어 있던 발행 및 이미지 처리, 평가 절차를 공용 하위 스킬 5종(`blog-publish`, `blog-images`, `skill-eval`, `skill-description-tune`, `skill-registry-review`)으로 분리했습니다.

가장 덩치가 컸던 `html-publish`는 디자인 시스템과 팔레트 사전이 카탈로그로 분리되면서 본문 크기가 127.6KB에서 11.2KB로 줄어 **91%의 감량**을 기록했습니다. 공용 하위 스킬을 `call` 블록으로 분리한 `skill-creator`는 36.6KB에서 12.9KB로 65% 줄었고, `digest-post`는 24.8KB에서 9.7KB로 61% 줄었습니다.

추출된 도메인 카탈로그는 조합 성격에 따라 두 가지 규칙(`composition`)으로 구분됩니다.

- **직교(`orthogonal`) 카탈로그**: 서로 독립된 선택 차원(`axis`)을 다루어 한 작업에서 여러 개가 동시에 결합될 수 있는 모듈입니다. 캐릭터 이미지 생성에 사용하는 세 카탈로그가 대표적입니다. `camera-framing`은 카메라 구도 32종을 제공하며 선택 차원은 `camera.shot-size`입니다. `character-acting`은 표정 근육 12종과 고개 각도 12종을 제공하며 선택 차원은 `subject.expression`과 `subject.head-angle`입니다. `lighting-setup`은 조명 배치 25종을 제공하며 선택 차원은 `light.setup`입니다. 이 세 카탈로그는 서로 충돌하지 않으므로 한 작업에 함께 로드됩니다.
- **번들(`bundle`) 카탈로그**: 같은 선택 차원에 속하며 서로 함께 선택할 수 없는 대안들을 제공하는 모듈입니다. 한 번에 최상위 1개(`top: 1`)만 선택해야 하며, HTML 발행 시 브루탈리즘과 스위스 그리드, 에디토리얼 매거진 가운데 하나의 디자인 체계를 고르는 프리셋이나 등장인물 중 누구의 외형 설정을 불러올지 정하는 캐릭터 설정 번들(차원: `subject.identity`)이 여기에 해당합니다.

![이젤에 세워진 두루마리 보드에 카메라, 웃는 얼굴, 조명 아이콘 타일 세 개를 하늘색 핀으로 꽂아 고정하는 치비 서소영](https://img.seosoyoung.eiaserinnys.me/images/skill-catalog-dynamic-linking/03-catalog-late-binding.png)

직교 카탈로그와 번들 카탈로그를 함께 쓸 때 해결해야 할 과제가 하나 더 남습니다. 범용 카탈로그와 특정 캐릭터 번들 사이의 **오버레이 바인딩(`bindings`)** 및 대용량 카탈로그의 **L1/L2 샤드(Shard) 분할**입니다.

표정 근육 카탈로그(`character-acting`)에는 특정 인물에 종속되지 않는 범용 안면 근육 기호(AU1+AU4, AU6+AU12 등) 사전만 들어 있습니다. 그런데 이미지 생성 모델에 텍스트로 된 근육 기호만 넘기면 화풍이 바뀌거나 캐릭터 고유 인상이 흔들리기 쉽습니다. 일관된 얼굴을 유지하려면 해당 캐릭터의 표정과 고개 각도, 조명을 미리 그려 둔 4×3(12칸) 레퍼런스 시트 이미지를 보조 입력으로 함께 넘기고, 그 시트의 몇 행 몇 열(`#r1c1`부터 `#r3c4`까지)을 참조할지 좌표로 지정해야 하거든요. 범용 표정 카탈로그에 특정 캐릭터 시트 경로를 적어 넣으면 범용성이 깨지고, 캐릭터 번들에 표정 이론을 다시 적으면 중복이 발생합니다.

```yaml
# 캐릭터 설정 번들(seosoyoung-canon) 메타데이터의 오버레이 바인딩 선언
axis: [subject.identity]
composition: bundle
bindings:
  - target_catalog: character-acting
    target_axis: subject.expression
    sheet_template: references/facs/{style}-facs-12.png
    grid: 4x3
  - target_catalog: lighting-setup
    target_axis: light.setup
    sheet_template: references/lighting/{style}-lighting-12.png
    grid: 4x3
```

이 딜레마를 풀기 위해 번들 카탈로그의 메타데이터에 `bindings` 필드를 도입했습니다. 스킬 로더가 `seosoyoung-canon` 번들과 범용 `character-acting` 카탈로그를 함께 선택하면, 번들의 오버레이 바인딩이 활성화되어(`active_bindings`) 해당 캐릭터의 4×3 레퍼런스 시트 템플릿과 격자 정보가 자동으로 연결됩니다. 아울러 대용량 카탈로그는 루트 본문(L1)과 하위 샤드(L2)로 분할해, 처음 로드할 때는 루트 요약과 샤드 색인 표(`이름 | 식별자 | 선택 단서`)만 주입하고 필요한 샤드만 추가로 읽도록 구성했습니다. 세 장의 레퍼런스 좌표 표를 하위 샤드로 분리하자 캐릭터 설정 번들의 첫 로드 분량은 8,093자에서 5,499자로 줄어들어 기본 주입 부담이 32% 감소했습니다.

## 4. 선언형 링크 블록(`call`, `include`, `pick`)과 `pins` 재현성 계약

카탈로그를 분리한 직후 처음 시도했던 연결 방식은 스킬 메타데이터에 활동 태그(`activity: image-gen` 등)를 달고, 서버가 사용자 요청(`intent`)과 태그 점수를 합산해 카탈로그를 자동 추천하는 암묵적 매칭이었습니다.

하지만 실제 운영 데이터로 시험해 보니 암묵적 매칭에는 분명한 한계가 있었습니다. 스킬 마크다운 본문을 읽어도 **어느 단계에서 어떤 카탈로그가 결합되는지 눈으로 보이지 않았고**, 포괄적인 요청이 들어오면 관련 없는 카탈로그까지 한꺼번에 함께 로드되었습니다. 외부 링크는 스킬 본문 밖의 메타데이터에 숨기는 대신, 그 정보가 실제로 쓰이는 마크다운 본문 위치에 선언형 코드 블록으로 명시해야 했습니다. 이에 따라 스킬 본문에 직접 삽입하는 ```` ```link ```` YAML 블록 문법 3종을 도입했습니다.

```markdown
<!-- 1. call: 하위 스킬 호출 지점 선언 (본문 인라인 없이 3줄 포인터로 전개) -->
```link
call: blog-publish
when: 워크트리에서 글을 쓰고 작업 브랜치와 PR까지 낼 때 (section=posts)
```

<!-- 2. include: 필수 카탈로그 또는 특정 절(section)의 결정론적 인라인 (누락 시 에러) -->
```link
include: blog-taxonomy
```

<!-- 3. pick: 선택 차원(axis) 기반 도메인 카탈로그 지연 바인딩 슬롯 -->
```link
pick: catalog
axis: [camera.shot-size, subject.expression, light.setup]
top: 3
optional: false
```
```

각 링크 블록은 결합 시점과 실패 처리 방식에 따라 세 가지로 구분됩니다.

- **`call`**: 실행 중 특정 조건(`when`)에서 다른 절차형 스킬을 호출하라는 위임 포인터입니다. 하위 스킬의 본문을 호출 전에 미리 합쳐 두는 대신 3줄짜리 요약 포인터로만 전개해 컨텍스트 소비를 막습니다.
- **`include`**: 시맨틱 리랭커를 거치지 않고 대상 문서 전체나 특정 절(`section: "절 제목"`)을 100% 결정론적으로 본문에 삽입합니다. 분류 체계나 핵심 검증 기준처럼 절대 빠져서는 안 되는 문서에 사용하며, 대상이 없거나 절 제목이 어긋나면 즉시 컴파일 오류를 반환합니다.
- **`pick`**: 지정한 선택 차원(`axis`)의 후보 카탈로그 중 현재 요청(`intent`)에 맞는 상위 `top`개를 골라 결합하는 지연 바인딩 슬롯입니다.

서버 컴파일러(`load_skill`)는 먼저 리랭커 없이 선택할 수 있는 후보를 확인합니다. 필수 `pick` 블록(`optional: false`)에서 후보 카탈로그 수가 남은 슬롯 수(`remaining_slots`) 이하라면, **시맨틱 리랭커를 호출하지 않고 즉시 선택합니다.** 이때 선택 이유는 `only`로 기록됩니다. 예를 들어 `camera.shot-size` 차원의 카탈로그가 `camera-framing` 하나뿐이고 슬롯이 1개라면, 리랭커 호출 비용 없이 0초 만에 결정론적으로 결합합니다. 리랭커가 필요한 대상은 후보가 여러 개인 경쟁 차원과 선택적 블록입니다. 경쟁 차원의 예로는 여러 캐릭터 중 하나를 고르는 `subject.identity`가 있습니다. 선택적 블록은 `optional: true`이며 최소 점수는 `0.25`입니다. 이 대상들을 한꺼번에 평가하므로, 리랭커는 스킬 로드당 한 번만 호출됩니다[^3].

### 컨텍스트 압축 뒤의 결정론적 재로드와 `pins` 계약

장시간 실행되는 에이전트 세션에서는 컨텍스트 윈도우가 가득 차면 대화 이력을 요약하는 컴팩션(Compaction)이 일어납니다. 컴팩션 직후 에이전트가 작업하던 스킬을 다시 로드할 때, 시맨틱 리랭커가 다시 돌아가서 처음과 다른 카탈로그를 골라버리면 작업의 일관성이 깨집니다. 또한 리랭커가 잘못 고른 카탈로그 하나만 에이전트가 수동으로 교체하고 싶을 때도 있습니다.

이를 해결하기 위해 `load_skill`의 입출력에 **`pins`(선택된 카탈로그 이름의 1차원 배열)** 계약을 설계했습니다. 초기 프로토타입의 적대적 코드 리뷰에서 중요한 쟁점이 하나 제기되었습니다. `pins`를 선택된 카탈로그 이름의 1차원 배열로만 두면, 한 스킬에 여러 `pick` 블록이 있거나 선택적 블록(`optional: true`)에서 **아무것도 선택하지 않았다는 빈 슬롯 결과**가 나왔을 때 재로드 시 블록 간 모호성이 생기지 않느냐는 지적이었습니다.

별도의 복잡한 2차원 배열을 도입하는 대신, 정적 린트 규칙과 런타임 차단 규칙 두 가지를 결합해 1차원 배열의 간결함을 유지하면서 이 문제를 해결했습니다. 첫째, 정적 린트 규칙(`W109`)으로 **단일 스킬에서 동일한 카탈로그가 두 개 이상의 블록에 후보로 중복 등장하는 것을 금지**해, 이름만으로도 어느 블록의 선택인지 1:1로 대응되게 만들었습니다. 둘째, 컴팩션 뒤 `intent` 없이 `pins`만 넘겨 재로드할 때는 **시맨틱 리랭커 호출을 원천 차단**해, `pins`에 없는 선택적 블록(`optional: true`)은 추가 탐색 없이 즉시 빈 슬롯(`reason: "no_intent"`)으로 결정론적 복원되도록 고정했습니다.

이에 따라 각 `pick` 블록의 남은 슬롯 수를 계산하는 공식과 `intent`, `pins`의 상호작용 규칙은 다음과 같이 작동합니다.

$$\text{remaining\_slots} = \text{top} - |\text{above}| - |\text{pinned}|$$

여기서 `above`는 앞선 `include`나 `pick` 블록에서 이미 본문에 펼쳐져 현재 블록의 후보 슬롯을 먼저 채운 것으로 간주하는 카탈로그 집합이고, `pinned`는 전달된 `pins` 배열과 일치해 우선 선택된 후보 집합입니다.

1. **초기 로드 (`intent` 제공, `pins` 생략)**: 경쟁 슬롯에 대해 시맨틱 리랭커를 1회 실행하고, 선택된 전체 카탈로그 목록을 `["color-palette", "lighting-setup", "seosoyoung-canon", "character-acting", "camera-framing"]` 같은 1차원 `pins` 배열로 돌려줍니다.
2. **컴팩션 후 무결성 재로드 (`intent` 생략, 이전 `pins` 전달)**: `intent`가 없으면 시맨틱 리랭커 호출을 차단합니다. `pins`에 기록된 항목은 해당 블록에 그대로 복원하고(출처 주석의 이유는 `pins`로 갱신), 핀이 없는 선택적 블록은 빈 상태로 유지하며 이유를 `no_intent`로 기록합니다. 실측 결과 리랭커 호출 0회, **0.04초에서 0.07초** 만에 이전과 동일한 카탈로그 조합과 본문 구조가 재현되었습니다.
3. **부분 수정 재로드 (`intent` 제공 + 교체할 이름만 `pins` 지정)**: 에이전트가 캐릭터 번들 하나만 다른 설정으로 바꾸고 나머지 블록은 `intent`에 맞춰 다시 고르고 싶다면, `pins: ["psychedelic-maid-canon"]`처럼 바꿀 이름만 담아 넘깁니다. 고정된 슬롯을 뺀 나머지 슬롯(`remaining_slots`)만 리랭커가 재평가합니다.

## 5. 정적 분석기(`skill_lint`)와 다중 언어 파서 단일화로 찾은 실전 버그들

스킬과 카탈로그가 선언형 링크로 연결되면, 전체 문서 트리는 하나의 거대한 소스 코드 저장소가 됩니다. 코드에 컴파일러와 정적 분석기(Linter)가 필요하듯, 스킬 트리에도 깨진 참조와 구조적 결함을 배포 전에 잡아내는 정적 린터(`skill_lint.py`)를 만들었습니다.

![하늘색 돋보기와 정밀 집게를 들고 두 개의 작은 두루마리 카드 사이에서 끊어진 하늘색 연결 실을 정교하게 이어 붙이는 치비 서소영](https://img.seosoyoung.eiaserinnys.me/images/skill-catalog-dynamic-linking/04-skill-linter-verification.png)

린터는 전체 132개 스킬과 11개 카탈로그에 걸쳐 **오류(`E001`부터 `E010`), 경고(`W101`부터 `W109`), 정보(`I201`부터 `I203`)** 규칙을 검사합니다.

- **문법 및 참조 무결성 오류(`E006`부터 `E010`)**: `E006`은 닫히지 않은 코드 펜스, 알 수 없는 키, 잘못된 타입 등 링크 블록의 문법과 YAML 스키마 오류를 검사합니다. `E007`은 `call`이나 `include`가 존재하지 않는 대상을 가리키는 깨진 링크를 잡습니다. `E008`은 `include`가 지정한 마크다운 절(`section`)이 대상 문서에 없거나 중복 헤딩이어서 참조가 모호해지는 경우를 차단합니다. `E009`는 `pick`에 등록된 후보 카탈로그가 하나도 없는 유령 선택 차원을 검사하고, `E010`은 `include` 대상 본문에 또 다른 `include`나 `pick` 블록을 중첩하는 구성을 금지합니다.
- **결합도 및 구조 경고(`W101`부터 `W109`)**: `W101`은 본문에 내부 UUID(`node_id`)를 하드코딩했는지 검사합니다. `W104`는 본문 크기의 상한 초과를, `W105`는 카탈로그 선택 단서(`sample_cues`) 단어의 본문 일치율 미달을, `W106`은 본문이 가리키는 공통 스크립트나 자산 파일 경로의 실존 여부를 검사합니다. `W107`은 `call` 블록이 스킬이 아닌 카탈로그를 호출하는 경우를 잡고, `W108`은 스킬 본문 노드에 병합되지 않은 하위 자식 카드가 남아 있는지 확인하며, `W109`는 한 스킬 내 여러 `pick` 블록에서 동일 카탈로그 후보가 중복 등장하는지를 검사합니다.

첫째는 **색인 조회 길이 절단(Truncation)으로 인한 조용한 스킬 누락**이었습니다. TypeScript 런타임 `load_skill` 컴파일러는 스킬 엔트리 색인 트리를 조회할 때 기본 문자 수 상한인 `max_chars=50,000`을 그대로 쓰고 있었습니다. 전체 스킬 수가 132개로 늘어나면서 색인 길이가 50,000자를 넘겼고, 트리 끝부분에 새로 추가된 6개 스킬(`blog-publish`, `blog-images`, `skill-eval`, `skill-description-tune`, `skill-registry-review`, `catalog-creator`)이 응답에서 조용히 잘려 나갔습니다. 개편 직후 `digest-post` 스킬을 시험 로드하자마자 컴파일러가 `call: blog-publish` 대상을 찾을 수 없다는 `missing_call` 경고를 반환한 덕분에 문제를 즉시 발견했지요. 색인 조회 시 문자 수 상한을 해제하고 응답에 절단 표시가 나타나면 즉시 실패하도록 고쳐 해결했습니다.

둘째는 **Python 린터와 TypeScript 서버 컴파일러 사이의 YAML 파서 불일치**였습니다. 정적 린터는 Python의 `PyYAML`(`SafeLoader`)을 사용하고, 런타임 `load_skill` 컴파일러는 TypeScript의 `yaml` 패키지를 사용합니다. `PyYAML`은 YAML 1.1 규격에 따라 `on`, `off`, `yes`, `no`를 불리언 `True`와 `False`로 해석하는 반면, YAML 1.2를 따르는 TypeScript 파서는 같은 값을 일반 문자열로 해석해 두 환경의 검증 결과가 일치하지 않았습니다. 저는 두 언어에 파싱 규칙을 따로 적는 대신, 정상 케이스와 에러 케이스 37개를 담은 단일 기준 테스트 벡터(`link_vectors.json`)를 만들고 Python과 TypeScript 양쪽 테스트 스위트가 동일한 JSON 벡터를 읽고 똑같은 오류 코드를 내도록 강제해 파서 드리프트를 근본적으로 없앴습니다[^4].

## 에이전트 하네스를 설계하는 실무자를 위한 제언

1. **새로운 오케스트레이션 계층을 추가하기 전에, 절차(Skill)에서 선택지 사전(Catalog)을 먼저 분리하십시오.** 스킬이 비대해지는 주된 원인은 제어 흐름이 복잡해서라기보다, 카메라 구도표나 디자인 프리셋 같은 도메인 선택지 데이터가 절차문 안에 정적으로 고정되어 있기 때문입니다. 이를 직교(`orthogonal`) 카탈로그와 번들(`bundle`) 카탈로그로 분리하는 것만으로도 스킬 크기의 60%에서 90%가 줄어듭니다.
2. **필수 규칙(`include`)과 확률적 선택(`pick`), 하위 위임(`call`)을 본문 안의 선언형 블록으로 구분하십시오.** 모든 연결을 시맨틱 검색이나 메타데이터 태그에 맡기면 에이전트는 필수 검증 게이트를 건너뛰거나 왜 이 문서가 주입되었는지 추적할 수 없게 됩니다. 후보가 하나뿐인 필수 슬롯은 리랭커 호출 없이 즉시 결합하고(`only`), 컨텍스트 압축 뒤에는 `pins` 배열로 이전 선택을 결정론적으로 재현해야 장시간 세션의 일관성이 유지됩니다.
3. **마크다운 지침서도 코드처럼 정적 린터(`skill_lint`)로 컴파일하십시오.** 에이전트는 참조 문서가 잘려 나가거나 절 제목이 바뀌어도 불평하지 않고 조용히 추측으로 누락된 절차를 채웁니다. 문서 사이의 참조 무결성과 크기 상한을 정적 분석기로 검사할 때 비로소 프롬프트 모음집이 엔지니어링 아키텍처가 됩니다.
